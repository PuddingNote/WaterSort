# 아키텍처 결정 기록 (WaterSort)

> "무엇을 했는지"가 아니라 "왜 이렇게 정했는지"를 남기는 문서. 실물 asmdef 등은
> 코드 자체가 말해주므로 여기서는 반복하지 않는다.

## 이 프로젝트의 성격: 범용 엔진 + WaterSort 테마

이 저장소는 **색깔 정렬(Water Sort류) 퍼즐의 범용 엔진을 이 프로젝트에서 먼저
만들고, 그 위에 "물병의 물" 테마를 얹는 순서**로 진행한다. 이후 다른 소재
(볼트-너트, 레고 블록 등)로 새 게임을 만들 때는 이 저장소를 통째로 복사해
Presentation 계층(아트/연출/사운드)만 교체하는 것을 전제로 한다. 그래서 게임
로직 쪽 코드는 "물"이나 "병"을 모르게 짜고, 테마 고유의 것(붓기 연출, 병 비주얼
등)만 별도 계층에 둔다. 근거: `색깔정렬게임_기획서_범용형.md` 5장(Core Logic
Layer vs Presentation Layer), `모바일_캐주얼_게임_재사용_노트.md` 1장.

## asmdef 프리픽스: `ColorSort` (WaterSort가 아님)

일부러 프로젝트 이름(WaterSort)이 아니라 장르 이름(`ColorSort`)을 어셈블리
프리픽스로 썼다. 이 저장소를 복사해 다른 소재의 게임을 만들 때, 로직
어셈블리 이름이 "WaterSort.Core"처럼 이전 게임 이름을 달고 있으면 오히려
헷갈린다 — 복사 후 지울 것과 남길 것을 asmdef 이름만 보고 구분할 수 있어야
하므로, 소재 무관 로직은 항상 `ColorSort.*`로 유지한다. (물/병 관련 프리젠테이션
코드는 UI 어셈블리 안에 네임스페이스나 폴더로만 구분하고, 별도 어셈블리로
쪼개지 않는다 — 배포 전까지는 테마가 하나뿐이라 어셈블리를 더 쪼갤 이유가
없다. 테마가 실제로 여러 개 공존해야 하는 상황이 오면 그때 다시 판단한다.)

## 레이어 구성

```
Assets/
  Scripts/
    Core/      ColorSort.Core     — Board, Container, Unit(색상) 등 순수 모델 + 이동 판정 규칙.
                                    noEngineReferences:true, UnityEngine 심볼 자체를 못 씀.
    Solver/    ColorSort.Solver   — Core만 참조. 힌트 솔버(최적 다음 수), 라운드 자동 생성
                                    (역방향 셔플), 난이도 점수화. 이 게임의 "AI" 자리에 해당하는
                                    도메인 계층 (재사용 노트 1장: 게임에 AI가 없으면 핵심 도메인
                                    이름으로 바꾼다 — 여기서는 퍼즐이므로 Solver).
    Managers/  ColorSort.Managers — 외부 SDK(광고 등) 연동. SDK 타입이 UI로 새어나가지 않게 여기서만 참조.
    UI/        ColorSort.UI      — MonoBehaviour, 코드 기반 UI(UiFactory/UiTheme), 렌더링/입력.
                                    물병 비주얼·붓기 연출 등 WaterSort 테마 코드도 지금은 여기 안에 위치.
  Editor/      ColorSort.Editor  — 디버그 도구 등 에디터 전용.
  Tests/EditMode/ ColorSort.Tests.EditMode — Core+Solver 순수 로직 단위 테스트. UI는 참조하지 않음.
  Scriptable Object/ — 밸런스 수치(팔레트, 난이도 커브 등)를 담는 SO 에셋.
```

`Core`/`Solver`에는 `[assembly: InternalsVisibleTo("ColorSort.Tests.EditMode")]`를
심어 뒀다 — 모델 setter를 `internal`로 캡슐화하면서도 테스트에서 원하는 보드
국면을 직접 구성할 수 있게.

## Core/Solver 구현 완료 (2026-08-21)

Board/Container/MoveRules/ClearChecker/BoardHistory/PuzzleSession(Core)과
RoundGenerator/HintSolver/DifficultyScorer(Solver)를 구현하고, 스크래치패드
`dotnet test` 하네스(재사용 노트 2장)로 Unity 없이 검증했다(2026-08-21 기준
18개 EditMode 테스트 통과).

**라운드 생성 — 역방향 생성 중 발견한 버그와 수정**: 처음엔 역연산(색 덩어리를
다른 막대로 옮기기)에서 "도착 막대도 색이 맞아야 한다"는 조건을 정방향
`MoveRules.CanMove`와 동일하게 걸었는데, 이러면 **한 막대 안에 서로 다른 색이
수학적으로 절대 섞일 수 없다**(실제로 생성해서 찍어보고 발견 — 병마다 항상
단색이었음). 도착 쪽 색 제약을 없애고(자리만 있으면 어떤 색 위에도 얹을 수
있게) 출발 쪽 안전 조건(덩어리를 전부 걷어내 다른 색이 드러나면 안 됨)만
유지하도록 고쳤다 — 이후 여러 시드에서 실제로 뒤섞인 배치가 나오고 항상
클리어 가능함을 확인.

**힌트/생성-검증 솔버 — BFS의 한계와 휴리스틱 탐색 도입**: 위 수정 후에도
9색×9칸 근처(기획서 6.5의 "101+" 최고난도 구간)에서 순수 BFS 최단경로 탐색이
500만 states를 뒤져도 답을 못 찾는 사례가 나왔다 — 실제로 못 푸는 보드가
아니라, 최단 해가 길어지면 가지치기 없는 BFS가 지수적으로 감당 못 하는
것(실제 Water Sort 솔버들이 A*/IDA*류를 쓰는 이유와 동일). **사용자 확인 후,
"색 전이(transition) 수"를 휴리스틱으로 쓰는 가중치 Best-First 탐색을
추가**했다(`HintSolver.FindSolutionHeuristic`, `MinHeap<T>`는 Unity 런타임
호환성 때문에 BCL `PriorityQueue` 대신 직접 구현). 최단 경로는 보장하지
않지만 "풀리는 경로 하나"는 최고난도 구간에서도 수 ms 안에 찾는다.
- 라운드 생성 검증(존재 여부만 필요) → 휴리스틱 탐색만 사용.
- 실제 힌트 버튼(`HintSolver.FindNextMove`) → 먼저 BFS(작은 예산)로 진짜
  최적수를 시도하고, 못 찾으면 휴리스틱 탐색으로 폴백 — 일반적인 플레이
  상태(어느 정도 정리된 보드)에서는 최적수를, 극단적으로 뒤섞인 상태에서도
  "유효한 다음 수"를 보장한다.

## 라운드 번호 → 파라미터 자동 매핑 + 자기대전 실측 (2026-08-21)

`RoundDifficultyCurve.SampleParameters(roundId, themeLimits, rng)`가 범용형
기획서 6.5/6.6(물병판 7.5/7.6)의 "라운드 구간별 목표 난이도" 표를 구현한다 —
**절대 수치가 아니라 테마의 [min,max] 범위에 대한 비율(fraction)로 구간을
정의**해서, 색상 팔레트 한도가 다른 소재(예: 6색뿐인 테마)에도 그대로
재사용된다(`ThemeLimits`만 테마별로 바꿔 끼운다). `RoundBuilder.Build(roundId,
limits, rng)`가 실제 게임이 부를 단일 진입점 — 샘플링→생성→실측
난이도(`DifficultyScorer`)가 목표와 너무 벗어나면 shuffleDepth를 조정해
재시도한다(기획서 6.6 의사코드의 "adjust params and retry" 그대로).

**자기대전 실측 결과(재사용 노트 3장 원칙)**: 라운드 1~150 구간을 라운드당
15회씩 헤드리스로 생성해 측정한 결과, 평균 색상 수(3.5→8.5)·슬롯 수
(4.3→8.8)·최단 클리어 수(5.7→17~18)·DifficultyScore(22→194)가 전부 우상향—
100 라운드 근처부터는 색상/슬롯이 테마 최대치에 근접해 완만해지지만 여전히
증가 추세. 라운드 1개 생성(검증+보정 재시도 포함) 평균 수 ms 이내로 실시간
생성에 문제없음. **단, 여기서 "실측"은 자기대전(솔버 기준 최단 클리어 수)
검증이지 실제 사람이 체감하는 난이도 검증이 아니다 — 사람 플레이테스트
기반 가중치/커브 계수 조정은 여전히 남아 있다** (아래 "아직 정하지 않은 것"
참고).

## 라운드 생성 방식 전면 교체: 역방향 셔플 → 완전 무작위 배분 (2026-08-22)

**문제**: 위 자기대전 실측은 "솔버가 몇 수만에 푸는가"만 쟀는데, 실제 UI로
플레이해보니(사용자 스크린샷) 병 하나에 같은 색이 4~7칸씩 연달아 붙어있고
"옮길 곳이 사실상 1개뿐"인 시시한 라운드가 나왔다. 원인은 역방향 셔플이
**항상 색 덩어리(연속된 같은 색 구간) 단위로만** 옮기는 구조라서 — shuffleDepth를
아무리 올려도(4.5~16배까지 올려봤다) 덩어리가 쪼개져서 잘게 섞이질 않고, 그냥
큰 덩어리가 이 병 저 병으로 옮겨 다닐 뿐이었다.

**해결**: `RoundGenerator`를 **완전 무작위 배분** 방식으로 다시 짰다 — 전체
유닛(색상 수 × 슬롯 수)을 한 뭉치로 모아 Fisher-Yates로 진짜 섞은 뒤 병에
나눠 담는다. 역방향 셔플처럼 "역연산이라 항상 풀린다"는 수학적 보장이
없으므로, 생성 직후 `HintSolver`로 실제로 풀리는지 검증하고 안 풀리면
재시도(그래도 안 되면 여유 막대를 늘려 재시도)하는 구조는 그대로 유지.

**부수 발견 — 여유 막대 수의 실제 역할**: "여유 막대가 적을수록 어렵다"고
가정했었는데, 완전 무작위 배분에서 실측해보니 그게 아니라 **여유 막대는
일정 수 밑으로 내려가면 그냥 안 풀리는 문턱값**이었다(색 10종·슬롯 8칸 기준
여유 막대 1개 = 100번 중 0~1번만 풀림, 2개 = 100번 중 99~100번 풀림). 그래서
`RoundDifficultyCurve`에서 여유 막대를 라운드가 오를수록 줄이던 로직을
없애고, 테마 최소치 자체를 2로 올렸다(`WaterPalette.ThemeLimits`). 이제
라운드 진행에 따른 난이도는 **색상 수 × 슬롯 수(총 유닛 수)** 가 전담한다 —
실측상 이것만으로도 1라운드 15~16수 → 최고난도 70수 이상까지 자연스럽게 늘어남.

**연쇄적으로 걷어낸 것들**: `RoundGenerator.Parameters.ShuffleDepth`(더 이상
의미 없는 개념), `DifficultyScorer.Score()`(가중합 추정치 — shuffleDepth가
없어졌고, 애초에 "실제 클리어 수"라는 훨씬 정직한 지표가 이미 있었다),
`RoundBuilder`의 "목표 점수와 비교해 재조정" 루프(같은 이유로 불필요해짐 —
이제 `RoundBuilder.Result.SolutionMoveCount`가 실측 난이도를 직접 보고한다).
`DifficultyScorer.MeasureColorSpread`(색 분포 통계)만 남겨 뒀다.

**난이도 상한 라운드: 200 → 50 → 100 → 200** (전부 사용자 피드백 기반 조정).
50으로 낮춰서 실제 플레이해본 뒤 "30·50라운드 체감 난이도가 마음에 든다,
다만 더 천천히 올라가면 좋겠다"는 확인을 받아 100으로 늘렸고, 이후에도
같은 이유("좀더 천천히 어렵게")로 다시 200까지 늘렸다(2026-08-25) —
`RoundDifficultyCurve.MaxDifficultyRoundId` 하나만 바꾸면 곡선 전체가 같은
모양으로 비례해서 늘어나는 구조라(진행도 = (roundId-1)/(cap-1)) 조정이 쉽다.
결과: 라운드 200의 파라미터·실측 난이도가 예전 라운드 100(=예전 라운드 50)과
거의 동일(색 10종·슬롯 8칸·약 70수대)하게 재현되고, 라운드 30/50/100은 그만큼
더 완만하게 쉬워짐 — 사람 체감 검증은 사용자가 직접 플레이하며 지속 조정 중.

## 기울어진 병 안의 물을 사다리꼴로 (액체답게) — 시도 2건 모두 롤백 (2026-08-31)

지금까지 붓는 병의 물(세그먼트)은 병 껍데기(`Visual`)와 함께 그냥 강체로
같이 회전한다 — 색깔 띠가 직사각형인 채로 통째로 기울어질 뿐이다. 물은
고체가 아니라 액체라서 병이 기울어도 수면은 수평을 유지해야 자연스럽다는
피드백을 받고(다른 게임 참고 이미지로 확인) 두 가지 방법을 시도했지만
둘 다 원하는 결과가 안 나와서 **전부 롤백하고 강체 회전으로 되돌렸다**
(`BottleView`/`PourAnimator` 둘 다 이 절 이전 상태 그대로).

- **1차 시도 — 수평 유지 컨테이너(`WaterLevel`) + `Mask`로 병 윤곽만큼
  잘라내기.** 실제로 플레이해보니 클리핑이 전혀 안 되고 물이 수평 상태
  그대로 병 윤곽과 무관하게 따로 노는 문제가 있었다. 정적 코드 분석으로는
  원인을 못 찾았다.
- **2차 시도 — 회전하지 않는 배경색 "지우개" 사각형**(물의 실제 수면 높이에
  바닥을 맞춰서, 강체 회전한 물 중 그 위로 튀어나온 부분을 가림). Mask보다는
  단순 `Image` 사각형만 써서 안전하다고 판단했지만, 사용자 확인 결과 이것도
  원하는 모습이 아니었다("이건 아닌 거 같은데 원래대로 돌려줘").

**결론**: 이 기능은 이 세션에서 더 진행하지 않고 보류한다 — 물병이 기울 때
물이 강체로 같이 회전하는 지금 모습으로 당분간 간다. 다시 시도할 때는 Unity
Editor에서 직접 눈으로 확인하며 반복할 수 있는 상태에서(현재처럼 스크린샷·
녹화를 여러 차례 주고받는 방식이 아니라) 진행하는 게 나을 것 — 두 시도 다
정적 코드로는 "이론상 맞아야 하는데 실제로 안 맞는" 종류의 문제였다.

## 물병 이미지 적용: 사각형 물이 시험관 윤곽 밖으로 삐져나오는 문제 (2026-09-01)

`UiSkin.BottleBackground`에 실제 시험관 그림을 넣어보니(사용자 제공), 물이 있는
병은 그냥 네모난 사각형으로 보이고 목이 좁아지거나 바닥이 둥근 시험관 모양이
전혀 반영 안 됐다 — 원인은 단순: 세그먼트(물)는 그냥 사각형이고, 병 그림은
그 사각형과 무관하게 별도 레이어로 뒤에 깔릴 뿐이라, 물이 있는 구간에서는
사각형이 시험관 윤곽을 완전히 덮어버려서 빈 병일 때만(세그먼트가 없어서) 실제
시험관 윤곽이 보였다.

**해결 시도 1 — 손으로 만든 정적 마스크 PNG**: 파이썬(Pillow)으로 병 그림을
분석해 마스크 PNG를 미리 계산해서 별도 파일로 만들었다. 동작은 했지만 병
그림을 바꿀 때마다 마스크도 손으로 다시 만들어야 하는 게 단점이었다.

**해결 시도 2 — 런타임 자동 계산(`BottleWaterMaskFactory`)**: 사용자가 "Mask
이미지를 새로 만들지 말고 기존 이미지만으로 안 되냐"고 요청해서, 런타임에
`UiSkin.BottleBackground` 스프라이트 하나만 보고(`Sprite.texture.GetPixels32()`로
알파 채널 분석) 마스크를 직접 계산하는 정적 클래스로 바꿨다 — 별도 그림
에셋이 없고 병 그림을 바꿔도 자동으로 다시 계산된다는 장점이 있었지만,
그 텍스처의 **Read/Write Enabled**를 반드시 켜둬야 하는 제약이 있었다.

**최종 — 사용자가 직접 그린 마스크 그림 + Unity `Mask` 컴포넌트 (2026-09-07)**:
사용자가 "Mask 이미지를 사용하는 방식으로 하면 어떻게 만들어야 하냐"고 물어서
Unity `Mask`가 요구하는 알파 규칙(불투명=보임, 투명=가려짐 — 런타임 마스크의
"구멍 뚫기" 오버레이와는 정반대 의미)을 설명했고, 사용자가 `bottle_empty.png`와
정확히 같은 캔버스 위에 실루엣 내부만 불투명, 나머지는 완전 투명인
`bottle_mask.png`를 직접 그려왔다. `UiSkin.BottleMask`에 연결하면 `BottleView`가
`Visual`과 `FillArea` 사이에 그 스프라이트를 쓰는 `Image` + `Mask`
(`showMaskGraphic = false`)를 끼워 넣어 물을 실루엣 밖으로 못 나가게 자른다.

붓기 애니메이션의 "기울어진 병 안의 물 사다리꼴" 시도에서 `Mask`가 원인 불명
버그를 냈던 것과는 성격이 다르다 — 그건 **회전하는 콘텐츠**에 Mask를 씌운
경우였고, 이건 회전 없는 고정 실루엣 클리핑이라 같은 실패 조건이 아니다. 이
방식은 런타임 팩토리와 달리 Read/Write Enabled가 필요 없다(스텐실 방식이라
CPU에서 픽셀을 읽을 필요가 없음) — 대신 병 그림을 바꿀 때마다 마스크 그림도
같이 새로 그려야 한다. `BottleWaterMaskFactory`는 이 방식으로 완전히
대체되어 삭제했다.

## 붓기 애니메이션 도입: 기울이기 + 곡선 물줄기 + 양쪽 물 높이 동시 변화 (2026-08-26)

`docs/GameDesign.md` TBD로 남아있던 붓기 연출 정책(소요시간 약 1초, 겹친
이동은 막지 않음, 사운드는 나중 것 우선)이 정해진 뒤 실제로 구현했다.

**렌더링 모델 교체가 먼저 필요했다**: 기존 `BottleView`는 슬롯(칸) 하나하나를
개별 Image로 두고 색을 즉시 바꿔치는 방식이라, "물이 조금씩 빠지고 조금씩
차오르는" 연속적인 변화 자체를 표현할 수 없었다(색이 팍 바뀌거나 안 바뀌거나
둘 뿐). 그래서 내용물을 **색상별 연속 구간(세그먼트)**으로 바꾸고, 세그먼트
하나의 높이(`sizeDelta.y`)를 직접 Lerp하는 방식으로 다시 짰다. 이동 규칙상
한 번의 이동은 항상 "출발 병 맨 위 세그먼트를 줄이고, 도착 병 맨 위
세그먼트를 늘리는(또는 새로 만드는)" 것 하나뿐이라 — 아래쪽 세그먼트들은
전혀 안 건드려도 된다는 걸 이용해 구현을 크게 단순화했다.

**세 가지 요소를 하나의 타임라인으로 동기화**(`PourAnimator`): 들어올려서
도착 병 위로 이동+기울이기(0.2s) → 물줄기+양쪽 물 높이 변화(0.6s, 동시 진행)
→ 제자리로 복귀+세우기(0.2s). 실제 물병 게임처럼 붓는 병이 받는 병 자리로
가서 붓는 그림이 나와야 한다는 피드백(2026-08-26)을 받고, 제자리에서 살짝만
기울이던 첫 버전에서 지금 방식으로 바꿨다 — 붓는 병(`BottleView.Root`)을
자기 줄(`HorizontalLayoutGroup`)에서 일시적으로 떼어내(자리엔 `LayoutElement`
크기만 맞춘 spacer를 남겨서 같은 줄 다른 병들이 안 밀리게 함) 화면 최상단
`EffectsLayer`로 옮기고, 도착 병 위쪽(도착 병 자신의 실제 화면 높이에 비례한
만큼 — 기기별 캔버스 스케일과 무관하게 항상 자연스러운 여유가 나옴)으로
이동시킨 뒤 기울인다. 물줄기는 `PourStreamGraphic`(커스텀 `MaskableGraphic`)이
두 병 입구 사이 2차 베지어 곡선을 두께 있는 리본 메시로 그린다 — Screen Space
Overlay Canvas와 궁합이 안 좋은 LineRenderer 대신 직접 메시를 만드는 쪽을
택했다(사용자 확정: 곡선). 도착 병은 기울이지 않는다(사용자 확정).

**붓는 병의 "바닥"이 도착 병 쪽으로 가던 버그 (2026-08-26 플레이 확인 후 수정)**:
처음 버전은 `Root`의 중심을 도착 병 위 어떤 지점으로 옮긴 뒤 그 상태로 기울이는
방식이었는데, 회전축(pivot)이 병 바닥 쪽(위 참고)에 있다 보니 축에서 먼
입구가 오히려 반대편(위·옆)으로 크게 튕겨나가고, 축에 가까운 바닥이 도착 병
쪽에 남아버렸다(사용자가 실제 플레이로 발견). "입구가 최종적으로 어디 있어야
하는지"를 먼저 정하고, 회전축 기하학을 거꾸로 풀어서 매 프레임 `Root.position`을
계산하는 방식(`BottleView.ComputeRootPositionForMouth`)으로 바꿔 해결 —
Root 중심이 아니라 입구 좌표를 직접 제어 대상으로 삼은 것이 핵심이다.

**물줄기가 아예 안 보이던 버그**: 처음엔 커스텀 `MaskableGraphic`(2차 베지어를
직접 메시로 그리는 방식)으로 구현했는데 실제 플레이에서 전혀 렌더링되지
않았다(정확한 원인은 특정하지 못함 — Overlay Canvas 위 커스텀 메시의 어떤
초기화/렌더 타이밍 문제로 추정). 이미 검증된 `UiFactory.CreateImage` 기반으로
바꿔, 곡선 경로를 짧은 회전된 사각형 Image 여러 개(세그먼트)를 이어 붙여
표현하는 방식으로 교체해 해결했다 — 버튼/물 세그먼트에서 이미 확실히 동작하는
같은 기법을 재사용한 것이라 신뢰도가 더 높다.

**물줄기 재조정 (2026-08-26 재확인 후)**: 곡선(짧은 사각형 여러 개를 베지어
경로로 이어붙임) 방식이 마디마다 꺾여 보여 부자연스럽다는 피드백을 받고 직선
하나로 단순화했다. 시작점도 입구의 "가운데"가 아니라 실제로 물이 흘러나오는
지점으로 고쳤다 — 병이 기울면 입구 양쪽 모서리 높이가 달라지는데, 그중 더
아래로 처진 모서리(`PourAnimator.SpoutWorldPosition`)가 실제 스파웃이다.
안 기울었을 때는 두 모서리 높이가 같아서 자연히 기존 중앙 계산과 같은 값이
된다. 물(세그먼트)이 기울기와 함께 시각적으로 기우는 것은 별도 구현이
필요 없었다 — 세그먼트가 이미 회전하는 `Visual`의 자손이라 구조적으로 항상
같이 기울어진다(출렁거림 같은 표면 애니메이션은 요구사항에서 제외 — 강체
회전만으로 충분).

**물줄기가 대각선으로 보이고 도착 병 안까지 안 이어지던 버그 (2026-08-26 재재확인)**:
붓는 병을 도착 병의 대략 위쪽 어딘가에 "hover"만 시켰지, 스파웃(기운 쪽
모서리)이 정확히 도착 병과 같은 X에 오도록 맞추지는 않아서 물줄기가 대각선으로
보였다. 물줄기 끝점도 도착 병의 고정된 입구가 아니라
`BottleView.WaterSurfaceWorldPosition()`(지금 차 있는 물의 실제 수면 —
차오르면서 매 프레임 같이 올라감)으로 바꿔 병 위쪽에서 뚝 끊기지 않고
자연스럽게 물까지 이어지게 했다.

**스파웃 목표 위치 계산 방식을 "미리 유도"에서 "측정 후 보정"으로 교체
(2026-08-26 삼재확인)**: pivot·패딩 값을 직접 손으로 유도해서 Root 위치를
역산하는 `BottleView.ComputeRootPositionForSpout`를 만들었는데도 물줄기가
여전히 완전한 직선이 아니었다 — 어디선가 유도 과정에 오차가 있었던 것으로
보이나 정적 분석만으로는 정확한 지점을 못 찾았다. 유도식을 더 정교하게
다듬는 대신 아예 다른 전략으로 바꿨다: 목표 각도로 잠깐 세팅해두고 스파웃이
**실제로 어디에 있는지 측정**해서, 목표 지점과의 차이만큼 Root를 그대로
옮긴다(`PourAnimator.PlayRoutine` 안에서 처리, 별도 메서드로 안 뺐음).
병진이동은 회전과 무관하게 그대로 더해지므로 이 보정은 근사가 아니라 항상
정확하다 — pivot 기하학이 아무리 복잡해도(또는 나중에 바뀌어도) 깨지지 않는다.
측정하는 동안 잠깐 각도를 바꿨다가 같은 프레임 안에서 되돌리므로 화면엔
전혀 안 보인다.

**초기 배치 시 물이 실제보다 얇게 보이던 버그**: `RebuildBottles()`가 병들을
만든 직후 곧바로 `Refresh()`로 첫 화면을 그리는데, 그 시점엔 아직 Unity의
레이아웃 그룹이 병의 실제 크기(120×420)를 확정하기 전이라 `FillArea.rect.height`가
기본값(더 작은 값)으로 읽혀 세그먼트가 얇게 그려졌다 — 그 병을 한 번이라도
옮기면(레이아웃이 이미 끝난 뒤라) 정상 크기로 저절로 고쳐지는 것처럼 보였다.
`RebuildBottles()`에서 초기 `RefreshAllBottles()` 직전에 `Canvas.ForceUpdateCanvases()`를
호출해 레이아웃을 강제로 먼저 확정시켜 해결했다.

**클리어 판정이 붓기 연출보다 먼저 일어나던 버그 (2026-08-31)**: `PuzzleSession.TryMove`는
탭한 그 순간 Board를 바로 바꾸는데, 화면은 `PourAnimator`가 붓기 연출로 서서히
따라잡는 구조다 — `GameView.OnBottleTapped`가 이동 직후 곧바로
`EvaluateBoardState()`를 불러 클리어 여부를 확인했더니, 마지막 병이 화면에
다 차는 걸 보여주기도 전에(Board 기준으로는 이미 클리어라) 바로 다음 라운드로
넘어가 버렸다. `PourAnimator.Play`에 `onComplete` 콜백을 추가하고, 성공한
이동의 `EvaluateBoardState()` 호출을 그 콜백으로 옮겼다. 겹친 이동까지
고려해서, `onComplete`는 "이 이동의 연출이 끝났을 때"가 아니라 "지금 진행
중인 모든 붓기 연출이 다 끝났을 때"(`PourAnimator`가 관리하는 활성 코루틴
목록이 0개가 되는 시점)에만 실행되게 했다 — 그래야 여러 병이 동시에
움직이고 있어도 화면이 실제로 다 안정된 뒤에만 클리어/교착 판정이 일어난다.

**붓고 있는 병 재선택 금지 (2026-08-31)**: 입력은 안 막지만(다른 병끼리 겹쳐서
동시에 움직이는 건 그대로 허용), 지금 붓고 있는 병(출발 병 — 자기 줄에서
떨어져 나와 원래 자리로 아직 안 돌아온 병)은 다시 탭할 수 없게 했다. 도착
병은 대상이 아니다 — 여러 병에서 같은 병으로 연달아 쏟아붓는 건 기존처럼
계속 가능해야 한다(둘 다 사용자 확정). `PourAnimator`가 `Play()` 시점에
`move.FromIndex`만 `_busySourceIndices`에 넣고, 연출이 끝날 때 뺀다.
`GameView.OnBottleTapped`는 맨 처음에 `PourAnimator.IsBusy(index)`만 확인하면
된다. Undo/Reset(`CancelAll`)은 `StopCoroutine`으로 코루틴을 강제로 끊어서
정상적인 정리 코드를 안 거치므로, `_busySourceIndices`도 거기서 따로 비워준다.

**히트박스와 그림을 분리**: `BottleView.Root`(탭 판정, 안 기울어짐)와
`BottleView.Visual`(실제로 기울어지는 배경+물, pivot을 바닥 쪽에 둠)을
나눴다 — 병이 기울어도 손가락 조작 영역은 고정된 사각형이어야 조작감이 안
흔들린다.

**입력은 막지 않는다**(사용자 확정) — 다른 병 이동이 애니메이션 도중 또
들어오면 그냥 각자 재생된다. 겹칠 때 물줄기는 나중에 시작한 쪽이 항상 캔버스
최상단(`SetAsLastSibling`), 사운드는 공유 `AudioSource` 하나를 매번 다시
`Play()`해서 이전 재생을 자동으로 끊는 방식으로 처리했다(별도의 정지
로직 없이 Unity `AudioSource.Play()`의 기본 동작만으로 해결됨). Undo/Reset은
그 반대로 `PourAnimator.CancelAll()`로 진행 중인 연출을 전부 끊고 즉시 최종
상태로 스냅한다 — 상태를 강제로 되돌리는 조작이라 연출이 남아있으면 안 된다.

## Undo/Reset 도중 붓던 병이 화면에 붕 뜬 채 고정되는 버그 (2026-09-07)

붓기 애니메이션이 재생되는 도중(병이 그리드에서 떨어져 나와 `EffectsLayer`에
붙어 기울어져 있는 상태)에 Undo를 누르면, Board 데이터는 정상적으로
되돌아가는데 그 병 하나만 화면에서 이상한 위치에 굳어버리는 버그가 났다
(스크린샷으로 확인).

**원인**: `OnUndoClicked`/`OnResetClicked`는 이미 `PourAnimator.CancelAll()`을
호출하고 있었지만, `CancelAll()`이 `StopCoroutine`만 부르고 끝냈다.
`StopCoroutine`은 그 코루틴이 멈춘 지점 **뒤**에 있는 코드(원래 부모/자리로
복귀, spacer 제거, 기울기 0으로 되돌리기)를 통째로 건너뛴다 — 그래서 병이
`EffectsLayer`에 부모가 붙은 채, 자유 앵커·기울어진 각도 그대로 남는다.
뒤이어 호출되는 `BottleView.Refresh`는 물 세그먼트(내용물)만 Board 기준으로
다시 그릴 뿐 `Root`의 부모/위치/회전은 전혀 건드리지 않으므로 이 문제를
가리지 못한다.

**대안으로 고려했던 것**: 붓는 도중엔 Undo/Reset 버튼 자체를 비활성화. 하지만
붓기 연출이 ~1초 걸리는데 그동안 매번 Undo가 막히면 조작감이 답답해진다.

**해결**: 버튼을 막는 대신 `CancelAll()`이 "자연 종료 때와 똑같은" 정리를
직접 수행하도록 고쳤다 — 진행 중인 붓기마다(`ActivePour`에 원래 부모/형제
인덱스/spacer를 기록해 둠) 코루틴을 멈춘 뒤 `SetTilt(0f)`, spacer 제거,
`SetParent`+`SetSiblingIndex`로 원래 자리로 되돌린다. 이러면 Undo/Reset은
지금처럼 붓는 도중에도 언제든 눌러서 즉시 반응하고, 병도 항상 제자리로
돌아온다.

## 병이 많이 찼을 때 맨 위 물 크기가 어긋나는 버그 (2026-09-07)

라운드 300(용량 8·5칸 병)에서 물이 거의 다 찼을 때 맨 위 물 세그먼트만
나머지보다 눈에 띄게 작게 보이는 버그가 났다(스크린샷으로 확인). 물이 얼마
안 찼을 땐 안 보이다가 용량에 가깝게 찼을 때만 드러났다.

**원인 1 — 두 그림을 각각 따로 늘려서 생기는 비율 어긋남**: `Visual`(병
그림)과 `WaterMaskRoot`(마스크 그림)는 각자 자기 RectTransform에 꽉 채워
독립적으로 늘어난다. 그런데 `FillArea`(물이 쌓이는 기준 영역, `UnitHeight =
FillArea.rect.height / Capacity`의 근거)는 그동안 그냥 `Visual` 가장자리에서
6px 안쪽으로 잡은 사각형이었다 — 병 그림 전체(목 부분 포함)를 기준으로 잡은
셈이다. 반면 마스크 그림은 목 부분을 빼고 몸통만 그려져 있어서, 실제로
물이 보이는 영역(마스크가 드러내는 영역)이 `FillArea`가 가정한 영역보다
세로로 더 짧다. 물이 얼마 안 찼을 땐 이 차이가 드러날 일이 없다가, 병이
거의 다 차서 맨 위 세그먼트가 그 어긋난 상단 구간까지 올라가면 그 부분만
마스크에 가려 짧아 보인다.

**원인 2 — `bottle_mask.png.meta`의 트리밍 사각형이 실제 그림과 안 맞음**:
`bottle_mask.png`를 프로젝트에 넣을 때 같이 만들어진 `.meta`의
`spriteSheet.sprites[0].rect`가 실제 그 그림의 알파 바운딩 박스가 아니라
`bottle_empty.png`의 값(x:47,y:81,w:257,h:694)을 그대로 베낀 것이었다(아마
손으로 옮겨적거나 복사하는 과정에서 실제로 다시 계산되지 않은 채 남음).
파이썬(Pillow)으로 실제 알파 바운딩 박스를 다시 계산해서(x:79,y:94,w:194,
h:626) `.meta`를 바로잡았다 — Unity가 실제로 그 그림을 다시 Import하기
전까지는 이 잘못된 값이 그대로 쓰이기 때문에, 그림 자체가 아니라 좌표
숫자만의 문제라도 실제 렌더링에 영향을 준다.

**해결**: `BottleView`가 `Sprite.rect`(둘 다 알파 기준으로 트리밍된, 같은
원본 캔버스 픽셀 좌표)를 직접 비교해서 "마스크가 드러내는 영역이 병 그림
기준 몇 %인지"를 런타임에 계산하고(`ComputeFillAreaNormalizedRect`), 그
비율을 `FillArea`의 앵커로 쓰도록 고쳤다 — 6px 같은 고정 픽셀 패딩 대신 두
그림의 실제 트리밍 크기 차이를 그대로 반영한다. 두 텍스처의 원본 캔버스
크기가 다르면(비교 자체가 무의미하므로) 경고만 남기고 예전처럼 (0,0,1,1)
전체 영역으로 대체한다. 이 방식은 병/마스크 그림을 나중에 다시 그려도
코드를 안 고쳐도 되고, 처음부터 손으로 비율을 맞춰 넣을 필요도 없다.

**교훈**: 서로 다른 텍스처의 스프라이트 두 장을 "같은 RectTransform에 각자
꽉 채워 늘리기"로 겹쳐 쓸 때는, Unity가 각 텍스처를 알파 기준으로 독립적으로
트리밍한다는 걸 반드시 감안해야 한다 — 트리밍된 크기가 다르면 겉보기엔 같은
캔버스에서 그린 그림이라도 늘어나는 비율이 서로 달라져서 어긋난다.

## 힌트: 하이라이트만 하던 걸 실제 이동 자동 실행으로 변경 (2026-09-07)

`GameDesign.md`에는 애초에 "솔버가 최적 다음 수 계산 후 자동 실행"이라고
적혀 있었는데, 실제 코드(`GameView.OnHintClicked`)는 그동안 출발/도착 병을
하이라이트만 해주고 실제 이동은 유저가 직접 탭해야 하는 상태였다 — 명세와
구현이 어긋나 있었다. 사용자 요청으로 명세대로 맞췄다: `HintSolver`가 찾은
이동을 `GameView.PerformMove(from, to)`로 바로 실행한다 — 이 메서드는 병을
두 번 탭해서 이동을 확정할 때와 완전히 같은 경로(`_session.TryMove` →
`PourAnimator.Play`)라서, 유저가 직접 옮긴 것과 동일하게 붓기 연출까지
그대로 재생된다. 힌트가 가리키는 출발 병이 마침 다른 이동으로 붓는
중이면(`PourAnimator.IsBusy`) 그 클릭은 무시한다 — 탭으로 직접 고를 때와
같은 규칙. 더 이상 하이라이트만 하는 경로가 없어져서 `_hintMove` 필드와
`HintHighlight` 색은 완전히 걷어냈다.

## 힌트를 누르면 붓기 연출이 렉 걸린 것처럼 중간부터 재생되는 버그 (2026-09-07)

위에서 힌트가 실제 이동을 자동 실행하도록 바꾸자마자 새 버그가 났다: 힌트를
누르는 순간 화면이 잠깐 뚝 멈췄다가, 다시 움직이기 시작할 땐 이미 붓기
연출의 1단계(들어올리기)가 다 지나가고 중간부터 재생되는 것처럼 보였다.

**원인**: `HintSolver.FindNextMove`(BFS 최대 2만 states, 실패 시 휴리스틱
탐색 최대 30만 states)를 `OnHintClicked`에서 메인 스레드로 그대로 불렀다 —
계산이 끝날 때까지 그 프레임이 통째로 멈춘다(실제 렉). 문제는 여기서 안
끝난다: 그 멈춘 실제 시간만큼 다음 프레임의 `Time.deltaTime`이 커지는데,
`PourAnimator.Tween`은 `t += Time.deltaTime`을 그대로 썼다 — 그래서 렉이
풀리는 그 한 프레임에 `t`가 애니메이션 구간을 통째로(또는 대부분) 건너뛸
만큼 확 올라가 버려서, 화면이 다시 그려질 땐 이미 상당히 진행된 상태부터
보이는 것처럼 나타났다.

**해결**:
- `GameView.OnHintClicked`을 `async void`로 바꾸고 `HintSolver.FindNextMove`
  호출을 `Task.Run`으로 백그라운드 스레드에 맡긴다 — Board/Container 등
  `ColorSort.Core`/`ColorSort.Solver`는 UnityEngine 의존이 전혀 없는 순수
  C# 코드라 스레드에서 돌려도 안전하다. 계산하는 동안 유저가 다른 조작으로
  실제 `_session.Board`를 바꿀 수 있으므로(입력을 막지 않음), 스레드에는
  미리 복제한 스냅샷만 넘긴다. `await` 이후는 Unity의
  SynchronizationContext 덕분에 자동으로 메인 스레드로 돌아오므로 그 뒤
  `PerformMove` 호출은 안전하다. 계산 중엔 `_hintInFlight`로 힌트 버튼을
  비활성화해서 중복 클릭을 막는다.
- `PourAnimator.Tween`에 `Time.deltaTime`을 `MaxFrameDelta`(1/30초)로 자르는
  안전장치를 추가했다 — 힌트 렉은 근본 원인을 고쳤지만, 앞으로 GC 등 다른
  이유로 프레임이 오래 걸리는 상황이 생겨도 최소한 애니메이션이 구간을
  건너뛴 것처럼 보이는 일은 없게 하는 별개의 방어 코드다.

렉은 없앴지만, 계산하는 그 수백 ms~수 초 동안 화면이 아무 반응 없이 가만히
있으면 "버튼이 안 눌렸나?" 싶은 빈 시간이 생긴다는 피드백을 받아서, 같은
날 `HintLoadingOverlay`(딤 배경 + 가운데서 도는 원형 스피너)를 추가했다.
`ConfirmDialog`와 겉모습은 비슷하지만(딤 배경 + Canvas 직속에 얹힘) 결정적
차이 하나: **입력을 막지 않는다**(사용자 확정 — 계산 중에도 다른 병 조작이나
버튼은 계속 눌려야 함) — 배경 패널과 딤, 스피너 전부 `raycastTarget = false`로
둔다(색이 `clear`라도 `raycastTarget`이 켜져 있으면 클릭을 막아버리는 게
실제 함정이라 배경 패널도 명시적으로 꺼야 했다). 스피너는 기존
`Resources/Sprites/circle.png`(원형 실루엣)를 `Image.Type.Filled` +
`fillMethod.Radial360`으로 파이 조각처럼 채우고, 그 이미지를 매 프레임 그냥
회전만 시키는 최소 컴포넌트(`SpinnerRotation`)를 붙여서 "빙글빙글 도는
로딩" 느낌을 낸다 — 별도 애니메이션 스프라이트 시트나 트위닝 라이브러리
없이 회전 + 부분 채움만으로 충분했다. `circle.png`는 병/물처럼 소재별로
바뀌는 테마 그림이 아니라 폰트처럼 항상 쓰는 시스템 UI 요소라 `UiSkin`이
아니라 `UiTheme.LoadingSpinnerSprite`가 `Font`와 같은 방식(코드에서 직접
`Resources.Load`)으로 불러온다. `OnHintClicked`에서 계산 시작 직후
`HintLoadingOverlay.Show`, `finally` 블록(계산이 끝나는 바로 그 순간 —
이동을 실행하기 직전)에 `Hide`를 불러서, 사용자가 요청한 "힌트 물병이
진행되는 타이밍에 로딩 화면이 사라짐"이 정확히 맞아떨어진다.

## 라운드가 많이 진행된 상태에서 Start를 누르면 잠깐 렉이 걸리는 문제 (2026-09-07)

힌트 렉과 원인이 같은 계열의 버그: 라운드가 많이 진행돼서(=어려워져서)
`GameBootstrap.ShowGame`이 `RoundBuilder.Build`를 메인 스레드에서 그대로
부르면, 그 안에서 보드를 생성하고(자체적으로 풀리는지 검증 포함) 실측 수까지
한 번 더 계산하는 과정이 눈에 띄게 오래 걸려 Start를 누르는 순간 화면이
잠깐 멈춘다. 라운드 클리어 후 다음 라운드로 자동 넘어갈 때도 같은
`ShowGame`을 타므로 동일하게 발생할 수 있다.

**해결**: 힌트 렉을 고칠 때와 같은 패턴 — `RoundBuilder.Build` 호출을
`Task.Run`으로 백그라운드에 맡긴다. 다만 이번엔 사용자가 "바로 끝나면 그냥
넘어가고, 오래 걸릴 때만 로딩 화면을 띄우자"고 명시적으로 요청해서,
`Task.WhenAny(buildTask, Task.Delay(UiTheme.LoadingOverlayShowDelayMs))`로
경합시켜 지정한 시간(150ms) 안에 안 끝나면 그때 가서만
`HintLoadingOverlay`를 띄운다 — 대부분의 쉬운 라운드는 로딩 화면이 아예 안
보이고, 정말 오래 걸리는 라운드에서만 나타난다. 그동안(로딩을 기다리는
동안이든 아니든) 이전 화면(타이틀 또는 클리어 직전 게임 화면)은 그대로 두고
새 화면이 준비된 순간에만 교체한다 — 화면이 잠깐 텅 비어 보이는 걸 막기
위해, 기존에는 새 화면을 만들기 전에 먼저 지우던 것을 새 화면이 다 준비된
뒤로 미뤘다. Start를 빠르게 연타해도 두 번 겹쳐 들어가지 않게
`transitioning` 플래그로 재진입을 막는다.

이 변경으로 라운드 클리어 직후 잠깐(로딩이 오래 걸리는 드문 경우) 이미
클리어된 이전 보드가 화면에 계속 인터랙션 가능한 채로 남아있는 아주 짧은
틈이 생긴다 — 다만 그 보드는 이미 클리어된 상태(같은 색 병들만 남음)라
`MoveRules`가 어차피 유효한 이동으로 안 받아줘서 실질적으로 문제는 없다.

## 같은 도착 병에 두 병에서 동시에 같은 색을 부으면 물이 갑자기 확 차오르는 버그 (2026-09-07)

여러 병에서 같은 도착 병으로 동시에 쏟아붓는 건 이미 허용된 조작인데
(사용자 확정), 그중 두 병이 **같은 색**을 붓는 경우에만 버그가 났다 — 각자
따로 재생될 때와 똑같이 부드럽게 두 번 채워져야 하는데, 실제로는 물이
멈춰있다가 갑자기 확 차올랐다.

**원인 1 — 세그먼트 공유**: `BottleView.BeginGrowTop`이 도착 병 맨 위
세그먼트가 이미 같은 색이면 그 **같은 `Segment` 객체**를 재사용했다. 두
붓기가 동시에 같은 세그먼트를 향해 각자 `growStart`(시작 시점 스냅샷)
`growTarget`(그 붓기만의 목표)을 따로 계산해 절대값으로
`SetUnitCount(Lerp(...))`를 매 프레임 부르다 보니, 두 코루틴이 서로의
진행값을 덮어쓰며 경합했다.

**원인 2 — 조기 Refresh가 아직 애니메이션 중인 세그먼트를 파괴**: 붓기
하나가 끝나면 `PourAnimator.PlayRoutine`이 `dest.Refresh(...)`를 불러
Board 기준으로 최종 스냅했는데, `Refresh`는 그 병의 세그먼트를 전부
파괴하고 다시 만든다. 두 붓기가 같은 병을 향하고 있으면, 먼저 끝난 쪽의
Refresh가 **아직 애니메이션 중인 다른 붓기의 세그먼트까지 같이 파괴**해
버렸다 — `ApplySegmentUnitCount`에 `if (segment.Image == null) return;`
방어 코드가 이미 있었던 걸 보면 이 경우 자체는 예상은 했었지만, 그 뒤로
그 붓기는 조용히 멈춘 채(더 이상 아무것도 안 그려짐) 있다가, **자기 차례가
돼서 자신의 Refresh가 불릴 때 Board 기준 최종값으로 한 번에 스냅**되어
"갑자기 확 차오르는" 것처럼 보였다.

**해결**:
- `BeginGrowTop`이 색이 같아도 항상 **새 세그먼트**를 만들도록 변경 — 같은
  색이라 세그먼트 경계가 안 보이니 여러 개가 쌓여도 시각적으로는 하나처럼
  보인다. 각 붓기는 이제 자기만의 세그먼트를 완전히 독립적으로 애니메이션
  하므로 서로 진행값을 덮어쓸 일이 없다.
- `PourAnimator`에 도착 병 인덱스별 "지금 그 병으로 들어오고 있는 붓기
  개수"(`_activeDestCounts`)를 추가해서, **같은 병을 향한 붓기가 전부 끝난
  마지막 순간에만** `dest.Refresh(...)`를 부르도록 변경 — 먼저 끝난 붓기가
  아직 진행 중인 다른 붓기의 세그먼트를 더 이상 파괴하지 않는다. 이 카운트
  갱신은 `PlayRoutine`이 정상 종료든 방어적 조기 종료(`shrink == null`)든
  항상 실행되는 `RunAndUntrack`(`Play`의 코루틴 래퍼)에 둬서 카운트가
  영영 안 줄어드는 누수를 방지했다(`_busySourceIndices`도 같은 이유로 거기
  있음). `CancelAll()`에서도 `_activeDestCounts`를 같이 비워서
  Undo/Reset이 끊어버린 붓기의 카운트가 안 남게 했다.

## 힌트를 더 못 찾을 때 화면 가운데 토스트 텍스트 (2026-09-07)

힌트가 다음 수를 못 찾으면(`HintSolver.FindNextMove`가 null) 그동안
콘솔 로그로만 남기고 화면엔 아무 반응이 없었다. 유저 요청으로 화면
가운데 잠깐 떴다가 사라지는 토스트 텍스트(`Toast`)를 추가했다 —
`GameView.OnHintClicked`의 `move == null` 분기에서
`Toast.Show(_canvasRoot, "NO HINT AVAILABLE")` 호출.

연출은 3단계(사용자가 정확히 지정): ① 가운데보다 `ToastRiseDistance`만큼
위에서 투명한 채로 생성 → 가운데로 부드럽게(smoothstep) 이동하며 동시에
투명→불투명, 도착과 동시에 멈춤 ② 잠깐 유지 ③ 위치는 그대로 두고
불투명→투명으로 사라짐. `CanvasGroup.alpha`로 불투명도를, `RectTransform.anchoredPosition`
Lerp로 위치를 같이 제어하는 코루틴 하나(`ToastRunner`)로 처리했다 —
`PourAnimator.Tween`과 같은 패턴(간단한 로컬 `Tween` 헬퍼 + smoothstep
이징)을 재사용. 텍스트는 프로젝트 전체가 쓰는 `UiTheme.Font`, 흰색
(`UiTheme.TextPrimary`) 그대로다. 입력은 막지 않는다(다른 오버레이들과
같은 원칙) — `raycastTarget`/`CanvasGroup.blocksRaycasts` 전부 끔.

힌트 외에 "더 이상 진행 불가" 류의 다른 상황(교착 상태 등)에서도 재사용할
수 있게 `Toast.Show(canvasRoot, message)`를 범용으로 만들어뒀다.

## 병 추가(광고 보상) 기능 최초 구현 (2026-09-08)

`Board.cs`의 오래된 doc 주석("병 추가 등으로 용량이 다른 Container가 섞일
가능성을 열어 둔다")이 이미 이 기능을 염두에 두고 설계돼 있었다 — 그
설계를 실제로 채워 넣었다. 광고 SDK는 아직 없어서, 이번 구현은 "버튼
누르면 광고 없이 바로 보상 적용"까지만이고 광고 시청 단계는 나중에
그 자리에 끼워 넣을 자리만 마련해 뒀다(`GameView.OnAddContainerClicked`
주석 참고).

**핵심 개념 — Capacity vs UnlockedCapacity**: `Container`가 새 필드
`UnlockedCapacity`를 갖는다(`Capacity`는 여전히 "이 병이 최종적으로 도달할
수 있는 크기"로 불변, 생성자에서 한 번만 정해짐). `FreeSlots`/`IsFull`
(그리고 그걸 쓰는 `IsResolved`)이 전부 `Capacity`가 아니라
`UnlockedCapacity` 기준으로 바뀌었다 — 안 열린 칸은 `MoveRules.CanMove`
입장에서 아예 존재하지 않는 것처럼 취급된다(`FreeSlots<=0`으로 자동 차단).
일반 병은 생성 시 `UnlockedCapacity == Capacity`(기존과 100% 동일하게
동작, 기존 테스트/호출부 전부 무변경으로 통과). 병 추가로 생기는 보너스
병만 `UnlockedCapacity=0`으로 시작해서 `Container.Unlock()`으로 한 칸씩
늘어난다. `Capacity`를 실제로 0으로 두는 방식은 시도하지 않았다 —
생성자가 `capacity<=0`을 막아 두고 있고(의도적인 불변식), 무엇보다
`BottleView.UnitHeight = FillArea.rect.height / Capacity`가 0으로
나누면 그대로 깨지기 때문에, "존재하되 아직 다 못 씀"을 표현하는
별도 필드가 필요했다.

**보너스 병은 어디서 생기나**: `RoundGenerator`/`RoundDifficultyCurve`는
전혀 안 건드렸다 — 난이도 계산·솔버 검증은 지금까지처럼 "일반 병들만으로
확실히 풀리는 라운드"를 그대로 보장하고, `RoundBuilder.Build`가 그 결과에
`board.AppendContainer(new Container(parameters.SlotCount, unlockedCapacity: 0))`
로 마지막에 하나 더 붙인다(사용자 확정: "모든 라운드의 마지막 물병"). 이미
검증이 끝난 뒤에 완전히 비어있고 못 쓰는 병을 더하는 것뿐이라 솔버 결과에
영향이 없다(항상 빈 병이라 `IsEmpty`로 소스/목적지 후보에서 자동 제외).
`Board`에는 컨테이너를 나중에 붙이는 public API가 없어서
`Board.AppendContainer`를 새로 추가했다.

**Undo/Reset과의 상호작용**: `GameDesign.md`에 2026-08-25에 이미 확정돼
있던 정책("병 추가는 광고를 소비해서 얻은 아이템 개념이라 Undo/Reset으로
없어지면 안 됨, 물 이동만 되돌아감")을 그대로 구현했다. Undo/Reset은
`BoardHistory`의 전체 스냅샷 교체 방식이라(행동 역산이 아님), 스냅샷을
뜬 시점 이후에 열린 칸은 스냅샷 자체엔 반영이 안 돼 있다 — 그래서
`PuzzleSession`이 `_bonusUnlockedAmount`(지금까지 누른 총 횟수)를
Board와 별개로 직접 들고 있다가, `TryUndo`/`ResetToInitial`로 Board를
통째로 갈아 끼울 때마다 `SyncBonusUnlock()`으로 그 값을 보너스
컨테이너에 다시 강제로 맞춘다(`Container.SetUnlockedCapacity` — 더하는
게 아니라 절대값으로 맞추는 별도 메서드, `Unlock`의 상대적 +1과 구분).

**화면(BottleView) — 아래부터 선명해지는 반투명 오버레이**: 물 마스크
때와 달리 이번엔 "물처럼 늘었다 줄었다 하는 사각형"이 아니라 "병 배경
그림 자체를 아래부터 조금씩 선명하게" 만들어야 했다. `Visual`(병 배경
Image)의 알파를 절반으로 낮춰 "베이스"로 깔고, 그 위에 원래 알파 그대로인
복사본 하나를 `RectMask2D`로 아래쪽 일부만 보이게 잘라서 얹는다 — 그
복사본 자체는 항상 병 전체 크기로 고정해 두고 부모(마스크)만 높이를
바꾸는 방식이라(FillArea 세그먼트와 반대로) 그림이 늘어나거나 찌그러지지
않는다. `RectMask2D`는 `Visual`의 자식이라 붓기 애니메이션 중 회전할 때도
그냥 같이 돌 뿐 상대 회전이 없어서, 예전에 "회전하는 콘텐츠 + Mask"에서
겪었던 원인 불명 버그(위 항목들 참고)와는 다른 상황이다. 일반 병(항상
`UnlockedCapacity==Capacity`)은 이 오버레이 자체를 생성 시점에 아예 안
만든다(매 라운드 딱 하나뿐인 보너스 병만 해당).

**후속 확정 (2026-09-08, 같은 날 바로 이어서)**:
- "누를 때마다 1칸씩"이 2026-08-25의 "슬롯의 20%씩" 정책과 다르다고
  물어봤더니, 의식적인 단순화라고 확인받았다 — 20%는 slotCount가 5의
  배수가 아닌 라운드(홀수 포함)에서 반올림이 어색해지는 문제가 있어서
  고정 1칸씩으로 정리(`GameDesign.md` 해당 TBD 항목도 체크 완료로 갱신).
- `WaterPalette.ThemeLimits.MaxContainerCount`를 12 → 11로 낮췄다 —
  보너스 병 1개가 항상 더 붙으므로 화면에 뜨는 병 총수는 이제 최대
  11+1=12개로, 이 기능 도입 전과 정확히 같은 수를 유지한다(사용자
  확정: "화면의 병은 최대 12개로").
- 잠긴(아직 안 열린) 부분의 알파 배율을 0.5 → 0.25 → 16/255로 더 낮췄다 —
  실제로 보니 구분이 잘 안 된다는 피드백(마지막은 2026-09-10 사용자 지정
  "alpha 16", `UiTheme.LockedBottleAlpha`).
- 그때(2026-09-10) 유리 하이라이트(`Highlight`)도 Visual과 똑같이 처리하도록
  맞췄다 — 잠긴 상태에선 하이라이트 전체를 `UiTheme.LockedHighlightAlpha`(16/255)로
  흐리게 깔고, 그 위에 열린 높이만큼만 원래 밝기(흰색 알파 1) 복사본
  (`_unlockedHighlightRect`)을 덧씌운다. Visual은 병 그림에 세로 굴곡이 있어
  `RectMask2D`+고정 크기로 잘랐지만, 하이라이트는 1px 높이 그라디언트를 세로로
  늘린 것이라 위 앵커(`anchorMax.y`)만 잘라도 안 찌그러져서 Mask를 안 쓴다.
  `ApplyLockedClipHeight`가 `_lockedClip`과 `_unlockedHighlightRect`를 같이 갱신.
- 보너스 병이 항상 빈 채로 시작하다 보니, 기존 "빈 병 최대 3개" 정책이
  실질적으로 최대 4개(일반 빈 병 3 + 보너스 1)로 깨져 있었다 — 사용자가
  이 어긋남을 지적해서 `MaxEmptyContainerCount`를 3 → 2로 낮췄다(일반 빈
  병 + 보너스 1 = 항상 정확히 3, 절대 안 넘음). `RoundDifficultyCurve.ClampContainerCount`가
  `emptyContainerCount`를 `[MinEmptyContainerCount, MaxEmptyContainerCount]`
  범위 밖으로 절대 안 내보낸다는 걸 코드로 직접 확인하고 진행함(막대 총
  개수를 맞추려고 빈 병을 늘리거나 줄이는 보정 로직이 있는데, 그 보정도
  이 범위 안에서만 움직인다). `MinEmptyContainerCount`는 여전히 2(그 밑으로
  내리면 무작위 배분 자체가 거의 안 풀림 — 위 클래스 doc 주석 참고)라서,
  Min=Max=2로 사실상 상수가 됐다 — 예전엔 라운드마다 2~3 사이를 무작위로
  오갔던 값인데 이제 항상 2. 부수 효과: 막대 총 개수 상한(`MaxContainerCount`=11)이
  안 바뀐 채로 빈 병 하한이 2에 고정돼 버려서, 가장 어려운 라운드의 색상
  수가 예전엔 이론상 10종까지 나올 수 있었지만 지금은 총 개수 제한에
  걸려 최대 9종으로 살짝 낮아진다(슬롯 수는 그대로 4~8칸 그대로라 전체
  난이도 곡선이 무너지진 않음, 색상 수 쪽만 끝단에서 살짝 평평해짐) —
  이건 요청받은 사항은 아니라 별도로 안 건드렸다.

## 물이 밋밋해 보이는 문제 — 유리 하이라이트가 물에 가려져 있었음 (2026-09-08)

사용자가 다른 게임 스크린샷과 비교하며 "그냥 팔레트에 색만 띡 칠한 느낌"이라고
지적했다. 병을 만들 때 일부러 유리 느낌을 주려고 `bottle_outline` 안쪽에
하이라이트를 그려 넣었는데도 안 보인다고 했고, "물보다 병을 캔버스 상위로
올리면 되지 않냐"는 직감을 스스로 제시했다 — **정확한 진단이었다**.

**원인**: `BottleView`의 렌더 순서가 `Visual`(병 그림, 하이라이트가 그려진
바로 그 레이어) → `WaterMaskRoot` → `FillArea`(물 세그먼트) 순이다. Unity
UI는 부모의 그림을 먼저 그리고 자식을 그 위에 그리므로, 물이 있는 구간은
전부 `FillArea`의 불투명한 색 사각형이 `Visual`의 하이라이트를 완전히
덮어버린다 — 병이 비어있을 때만(물이 없어서 가릴 게 없을 때만) 반짝임이
보였을 것이다.

**해결**: 병 그림 전체를 물 위로 옮기는 대신(그러면 불투명한 테두리까지
같이 앞으로 나와서 물 자체가 안 보이게 됨), **하이라이트 전용 오버레이
레이어**를 새로 만들어 물(`FillArea`)보다 나중에(=형제 순서상 뒤에, 같은
마스크 부모 밑에) 그린다 — `UiSkin.BottleHighlight`(신규 필드)에 반투명
빛줄기 그림을 연결하면 `BottleView`가 물 세그먼트 바로 위에 얹는다.
`BottleMask`가 있으면 같은 `Mask` 안에 들어가 있어서 실루엣 밖으로는 안
튀어나온다. 물 색이 뭐든 이 오버레이는 항상 같은 자리에 항상 같은 모습으로
보인다 — 참고 이미지에서 병마다 색이 달라도 대각선 빛줄기가 똑같이 걸쳐
있는 것과 같은 원리.

**추가로 제안한 것 — 코드 수정 없이 그림만으로 되는 부분**: `UiSkin.WaterFill`이
지금 비어 있어서(`fileID: 0`) 물 세그먼트가 완전한 단색 사각형으로 나오고
있었다 — 이것도 "밋밋함"의 큰 원인이다. `WaterFill`은 이미 "흰색/밝은 회색
바탕이면 `WaterPalette` 색으로 자동 틴트"되는 구조라서, 그 바탕 그림
자체에 세로 명암(왼쪽 밝게·오른쪽 어둡게 등 유리 원통 느낌)을 그려 넣기만
하면 색마다 자동으로 같은 명암이 생긴다 — 코드 변경이 전혀 필요 없다.
`docs/Sprites.md`의 `water_layer` 행을 이 방향으로 갱신했다(예전 "그라디언트
최소화" 지침을 뒤집음 — 그 지침 자체가 지금 지적받은 밋밋함의 원인이었음).

**후속 — 그림 넣어서 실제로 확인해보니 롤백함 (같은 날)**: 사용자가
`glass_highlight.png`(AI 생성 대각선 빛줄기)를 만들어 `UiSkin.BottleHighlight`에
연결해서 인게임으로 확인했는데, 결과가 이상해 보였다. 확인해보니 그
그림의 `.meta` 트리밍 사각형이 실제 알파 영역과 안 맞는 값이었다(이번에도
`bottle_empty.png` 값을 그대로 베낀 것 — 이 프로젝트에서 새 스프라이트를
추가할 때 반복적으로 나타난 패턴, `bottle_mask.png` 때와 동일한 종류의
버그)이라 그것부터 바로잡았는데, 다시 봐도(사용자 표현) "그냥 별로"였다 —
레이어 순서(물 위에 그리기)는 의도대로 동작했지만, 실제 비주얼 결과 자체가
만족스럽지 않아서 **기능 자체를 롤백**했다: `UiSkin.BottleHighlight` 필드,
`BottleView`의 오버레이 생성 코드, `UiSkin.asset`의 연결, `glass_highlight.png`
에셋을 전부 제거했다. `docs/Sprites.md`의 `bottle_highlight` 행도 "낮음
우선순위, 선택 사항"이던 원래 상태로 되돌렸다.

이 시도에서 남는 건: (1) **레이어 순서 진단 자체는 맞았다** — 다시 시도할
때(다른 그림으로, 또는 다른 방식으로) 참고할 수 있게 원인 설명은 위에
그대로 남겨 둔다. (2) 새 스프라이트를 넣을 때마다 `.meta`의 트리밍
사각형이 이전 파일 값을 베껴서 잘못 들어가는 문제가 세 번째로 재현됨 —
Unity 에디터에서 직접 임포트하지 않고 파일을 바로 떨어뜨려 넣는 방식이라
생기는 문제로 보이는데, 근본적으로 막을 방법은 아직 없고 매번 발견해서
고쳐주는 수밖에 없다.

## 붓는 동안 물줄기 시작점이 병 그림과 살짝 어긋나는 문제 (2026-09-08)

`BottleMask`와 `BottleBackground` 두 그림의 윗부분(입구 쪽 모서리) 모양이
살짝 달라서, 물줄기 시작점(`SpoutWorldPosition` — `FillArea`, 즉 마스크
기준으로 계산됨)이 실제 병 그림의 입구 위치와 미세하게 안 맞았다. 사용자가
Scene 뷰에서 기울어진 병의 `Visual` RectTransform Left/Right 오프셋을 직접
끌어보면서 (오른쪽으로 기울 때 기준) Left -18 / Right 18로 맞으면 자연스러워
보인다는 걸 확인했다 — 이는 `Visual`을 가로로 18px만큼 통째로 미는 것과
같다(스트레치된 RectTransform에서 Left/Right 오프셋을 같은 값으로 맞추면
크기는 그대로 두고 위치만 옮겨진다).

**시도 1 — `Visual` 전체를 밀기 (실패, 화면상 아무 변화 없음)**: 처음엔
`Visual.offsetMin/offsetMax.x`를 같은 값으로 맞춰서(사용자가 확인한 -18/+18)
붓는 동안 병 그림을 통째로 옆으로 미는 방식으로 구현했는데, 실제로 적용해
보니 **적용 전후가 완전히 똑같았다**(사용자가 직접 확인). 원인은
`PourAnimator`의 "스파웃을 측정해서 목표 위치와의 차이만큼 `Root`를
옮긴다"는 델타 보정 로직이었다 — `WaterMaskRoot`(마스크+물, `FillArea`가
그 자손)가 그때는 `Visual`의 **자식**이었기 때문에, `Visual`을 얼마를
밀든 `WaterMaskRoot`도 정확히 같이 밀리고, 델타 보정이 그 이동분을
측정해서 `Root` 위치로 고스란히 상쇄해버렸다 — 결과적으로 병 전체(그림+
마스크+물)가 항상 원래 자리로 돌아와 시각적 변화가 0이 됐다. 즉 이
델타 보정은 "그 안에 뭐가 들었든 병 하나를 통째로 얼마나 밀든 다시
제자리로 돌려놓는" 성질이 있어서, **그 안에서 서로 상대적으로 움직이는
게 없으면 어떤 보정을 넣어도 무효**하다는 걸 뒤늦게 알게 됐다.

**시도 2 — 물 쪽만 독립적으로 밀기 (성공)**: `WaterMaskRoot`를 `Visual`의
자식이 아니라 **형제**(`Root`의 직속 자식)로 옮기고, 회전(`SetTilt`)과
피벗(`0.5, VisualPivotY`)만 `Visual`과 똑같이 맞춰서 같은 병처럼 같이
기울되, 좌우 오프셋(`SetWaterHorizontalOffset`)은 `Visual`과 완전히
독립적으로 줄 수 있게 했다. 이제 물 쪽에 오프셋을 주면: 델타 보정이 그
오프셋을 상쇄하도록 `Root`를 반대 방향으로 옮기고, 그 결과 물(FillArea)은
정확히 원래 목표 위치에 그대로 있고, `Visual`(병 그림, 오프셋을 안 받은
쪽)만 `Root`를 따라 반대 방향으로 실제로 움직인다 — 이게 바로 원하던
"병 그림만 옆으로 슬쩍 밀린" 결과다. 부호는 `sign`(도착 병이 오른쪽/왼쪽에
있는지)의 **반대**를 써야 한다(`fullNudge = -sign * UiTheme.PourVisualHorizontalNudge`)
— 물 쪽에 준 오프셋과 화면에 보이는 병 그림의 이동 방향이 위 상쇄
메커니즘 때문에 서로 반대이기 때문이다. 기울기 진행률(`e`)에 비례해서
같이 애니메이션되고, 스파웃 위치를 미리 측정하는 단계에도 똑같이
적용해서(그래야 측정값 자체가 보정 반영됨) 계산이 어긋나지 않는 건
시도 1과 동일. `PourAnimator.CancelAll()`(Undo/Reset 중 붓기가 끊기는
경우)에도 `SetTilt(0f)`와 짝을 맞춰 `SetWaterHorizontalOffset(0f)`로
리셋한다 — 안 그러면 취소된 병의 물 쪽이 밀린 채로 굳어버린다.

**교훈**: "측정해서 목표 위치로 되돌리는" 델타 보정 로직이 있는 곳에서는,
그 보정이 참조하는 대상(여기선 `FillArea`/물 쪽)을 직접 밀면 반드시
상쇄되어 무효화된다 — 뭔가를 상대적으로 움직이려면 그 대상이 아니라
"같이 움직이지만 보정 대상은 아닌 다른 요소"(여기선 병 그림)를 고정해
두고, 보정 대상 쪽을 밀어서 간접적으로 반대편이 움직이게 만들어야 한다.

### 후속 버그 — 이 보정 때문에 붓는 동안 물이 병 밖으로 삐져나옴 (2026-09-08, 사용자가 영상으로 제보)

위 "시도 2"가 물줄기 정렬 자체는 고쳤지만, 부작용을 놓쳤다: `fullNudge`를
`SetWaterHorizontalOffset`로 **Tween 내내(들어올리는 동안·붓는 동안·
복귀하는 동안 계속) 실제로 렌더링에 걸어뒀다.** `WaterMaskRoot`는
마스크(`BottleMask`, 실루엣 클리핑)와 실제 물 콘텐츠(`FillArea`/세그먼트)를
전부 담고 있는 컨테이너라, 이걸 통째로 옆으로 밀면 마스크의 실루엣
자체가 `Visual`(병 그림)의 실루엣과 어긋나 버린다 — 물은 여전히 자기
마스크 안에는 잘 잘리지만, 그 마스크 자체가 병 그림보다 옆으로 삐져나온
자리에 있으니 결과적으로 "물이 병 유리 밖으로 삐져나온" 것처럼 보였다
(사용자 스크린샷: 기울어진 병 안의 물 띠가 유리 테두리 오른쪽으로 튀어나와
있음). 위 "교훈"과 정확히 같은 함정이었는데 이번엔 반대 방향으로 걸렸다 —
델타 보정용으로 잠깐 측정할 때 쓰는 값을 그대로 **지속적인 렌더링 오프셋**으로도
같이 써버린 것.

**수정**: `fullNudge`를 Tween의 각 프레임에 지속적으로 걸어두는 걸 완전히
그만뒀다(`PourAnimator.PlayRoutine`의 1)/3) 단계에서 `SetWaterHorizontalOffset`
호출 자체를 제거). 대신 "스파웃 월드 좌표가 필요한 바로 그 순간"에만
`SetWaterHorizontalOffset(fullNudge)` → `SpoutWorldPosition(source)` 측정 →
`SetWaterHorizontalOffset(0f)` 원상복구를 같은 프레임 안에서 동기적으로
실행한다 — 원래도 `hoverRootTarget`을 구하는 최초 1회 측정은 이미 이
패턴이었고(애니메이션 시작 전에 측정하고 바로 되돌림), 이번에 `UpdateStream`
(붓는 동안 매 프레임 물줄기 시작점을 다시 계산하는 곳)에도 같은 패턴을
추가로 적용했다. `Update`/렌더 사이에 코루틴이 `yield`로 끊기지 않는 한
(둘 다 같은 동기 호출 안에서 걸었다 바로 풀므로) 화면엔 오프셋이 걸렸던
순간이 전혀 노출되지 않고, 물/마스크(`_waterVisual`)는 항상 오프셋 0으로
그려져 `Visual`과 완전히 겹친 채로만 움직인다 — 물이 다시는 유리 실루엣
밖으로 나올 수 없다. 물줄기(Stream)의 시작점 계산 결과는 수학적으로
이전과 동일하다(같은 `Root`/기울기 상태에서 같은 `fullNudge`로 측정하므로).

**추가 교훈**: 델타 보정 계산을 위한 "측정용 임시 오프셋"과 "실제로 화면에
보여줄 지속적인 오프셋"은 서로 다른 개념이다 — 전자는 반드시 매번 걸었다
그 자리에서 바로 되돌려야 하고, 후자로 착각해서 Tween 내내 유지해버리면
그 오프셋이 걸린 대상 전체(마스크 포함)가 시각적으로 밀려버린다.

## 병 추가 버튼에 AdMob 보상형 광고 연동 (2026-09-08)

병 추가 버튼이 그동안은 누르면 광고 없이 바로 보상이 적용되는 임시 동작이었는데
(GameDesign.md에 이미 확정돼 있던 "부분 완성 병 즉시 사용 가능"/"Undo·Reset과
무관하게 유지" 정책은 이 시점에 이미 구현돼 있었음), 이제 실제 Google AdMob
보상형 광고로 이어붙였다.

**중요한 제약 — SDK 설치는 이 세션이 직접 못 한다**: Google Mobile Ads Unity
Plugin은 Unity 패키지 매니저로 설치되는 패키지가 아니라, `.unitypackage`를
GitHub 릴리스에서 받아 에디터에서 직접 Import Package로 넣어야 하는 절차라
(+ External Dependency Manager로 네이티브 안드로이드 의존성까지 별도로
resolve해야 함) 파일만 편집하는 방식으로는 설치할 수 없다. 그래서:
- 실제 `GoogleMobileAds.Api` 사용 코드는 전부 `#if ADS_ENABLED`로 감싸서,
  SDK가 없어도(즉 지금 당장도) 프로젝트 전체 컴파일이 절대 안 깨지게 했다
  — `ADS_ENABLED`가 꺼져 있으면(기본값) `RewardedAdService`는 항상
  "광고 없음"으로만 동작해서, 병 추가 버튼이 계속 비활성화된 채로 있는
  게 정상이다. 이게 우연히도 이미 확정돼 있던 "광고 로드 실패 시 그
  자리에서 비활성화" 정책과 완전히 같은 코드 경로다.
- 사용자가 직접 해야 하는 설치 단계 4개(`RewardedAdService.cs` 상단
  doc 주석에도 그대로 적어 둠):
  1. https://github.com/googleads/googleads-mobile-unity/releases 에서
     최신 `GoogleMobileAdsPlugin.unitypackage`를 받아 Assets > Import
     Package > Custom Package로 임포트(딸려오는 External Dependency
     Manager 포함).
  2. Assets > External Dependency Manager > Android Resolver > Resolve
     실행(네이티브 안드로이드 의존성).
  3. Assets > Google Mobile Ads > Settings에서 App ID에
     `ca-app-pub-6387288948977074~1221971886` 입력 후 저장(빌드 시점에
     AndroidManifest에 자동으로 채워 넣어짐 — 손으로 매니페스트 건드릴
     필요 없음).
  4. Player Settings > Other Settings > Scripting Define Symbols(Android
     탭)에 `ADS_ENABLED` 추가.
  이 네 단계가 끝나야 실제 광고가 뜬다. 참고로 실제 광고 단위 ID
  (`ca-app-pub-6387288948977074/3903975543`, `AdUnitIds.BonusContainerRewarded`)를
  그대로 넣었는데, 테스트 중엔 AdMob이 무효 트래픽으로 판단해 계정에
  불이익을 줄 수 있으니 개발 중엔 자기 기기를 테스트 기기로 등록하거나
  당분간 Google 공식 테스트 광고 단위 ID로 바꿔서 확인해 보는 걸 권장한다
  (실제 배포 직전에 다시 이 ID로 돌리면 됨).

**구조**: `ColorSort.Managers`(광고/재화 담당으로 애초에 마련해 둔 asmdef)에
두 파일을 새로 뒀다.
- `AdUnitIds.cs` — 실제 광고 단위 ID 상수 모음. 지금은 병 추가용 하나뿐이고,
  나중에 힌트 등 다른 버튼에 광고를 붙이게 되면 여기 상수만 추가하면 된다.
- `RewardedAdService.cs` — adUnitId를 인자로 받는 범용 서비스(`IsReady`/
  `Preload`/`Show`). 병 추가 전용으로 짜지 않고 재사용 가능하게 만들었다
  — "나머지 버튼은 나중에" 요청이 이미 예고돼 있었기 때문.

**확인 창 추가 (2026-09-10)**: 버튼을 누르면 곧바로 광고가 뜨는 게 아니라,
먼저 "Watch AD\nto get extra bottle?" 확인 창(뒤로가기 창과 같은
`ConfirmDialog`, 왼쪽 `NO` / 오른쪽 `Yes`)을 띄운다. 그때 제목↔버튼 간격이
빡빡해서 `ConfirmDialog`의 제목/버튼 y오프셋을 -90/70 → -64/44로 벌렸다
(세 확인 창 전부 공용). `OnAddContainerClicked`는
이제 `_activeDialog`에 이 창만 띄우고, `Yes` 콜백에서 `ShowBonusContainerAd`를
불러야 실제 `RewardedAdService.Show`가 돈다(광고 재생 로직 자체는 그대로
`ShowBonusContainerAd`로 분리). `_activeDialog` 가드를 공유해서 뒤로가기
창과 동시에 뜨지 않고, Escape로도 닫힌다.

**흐름**: `GameView.Initialize`가 라운드 시작 시 `Preload`를 미리 불러서
버튼을 누르는 순간 바로 뜨게 해 둔다(로드는 비동기라 탭한 뒤에야 요청하면
그 자리에서 못 보여줄 수 있음). `ShowBonusContainerAd`는
`RewardedAdService.Show`를 부르고, **광고를 끝까지 다 봐야만**
`onRewardEarned` 콜백 안에서 `TryUnlockBonusContainer`를 부른다 — 중간에
닫으면(`onClosedWithoutReward`) 조용히 아무 일도 안 하고, 광고가 아직
준비 안 됐으면(`onUnavailable`) 역시 대체 지급 없이 무시한다(2026-08-25에
이미 확정된 정책). 광고를 한 번 쓰면(성공/실패 무관) `RewardedAdService`가
내부적으로 다음 광고를 자동으로 다시 로드해 둔다.

**버튼 비활성화 타이밍 문제와 `AdReady` 이벤트**: `_addContainerButton.interactable`은
이제 "잠긴 칸이 남아 있는지"뿐 아니라 "광고가 지금 당장 준비됐는지"도
같이 본다. 문제는 광고 로드가 비동기라, 로드가 막 끝나는 그 순간엔 아무도
`RefreshHighlights()`를 다시 안 불러서 버튼이 몇 초간 비활성 상태로 멈춰
있는 것처럼 보일 수 있었다 — `RewardedAdService`에 `AdReady`
static 이벤트를 추가하고 `GameView`가 구독해서, 로드가 끝나는 즉시
`RefreshHighlights()`를 다시 부르도록 했다. static 이벤트라 `GameView.OnDestroy`에서
반드시 구독 해지해야 한다(안 그러면 라운드가 바뀔 때마다 죽은
GameView 인스턴스를 계속 참조하는 델리게이트가 쌓임) — 새로 추가한
`OnDestroy`가 이 해지만 담당한다(이 프로젝트에서 `GameView`가 `OnDestroy`를
쓰는 첫 사례).

## 라운드 클리어 → "STAGE CLEAR" 연출 → 다음 라운드 자동 진행 (2026-09-08, 재확정)

그동안은 라운드가 클리어되면(`GameView.EvaluateBoardState`가 `IsCleared`
감지) `GameBootstrap`이 아무 연출 없이 바로 다음 라운드를 만들어 화면을
바꿔치기했다. 첫 구현(검은 배경 + 텍스트를 CanvasGroup 하나로 묶어 2초)을
보여줬더니 "이 느낌이 아니다"는 피드백을 받아 같은 날 다시 정확한 타임라인을
받아 재구현했다:
- **0~1초(페이드인)**: 텍스트 0%→100% 불투명, 배경(딤)도 함께 0→목표
  알파로 등장.
- **1~2초(유지)**: 텍스트/배경 그대로 유지한 채 뒤에서 실제 라운드 전환
  실행(다음 라운드 생성 + 화면 교체).
- **2~3초(페이드아웃)**: 텍스트 100%→0%. 배경은 텍스트 알파가 자기 목표치
  보다 높은 동안은 고정돼 있다가, 텍스트 알파가 그 밑으로 내려오는 순간부터
  텍스트와 정확히 같은 값을 취하며 함께 0까지 내려간다("모든 화면이
  자연스럽게 투명해지는 것처럼" — 사용자 확정).

총 약 3초(2구간이 라운드 생성 속도에 따라 길어질 수 있어 "약").

**배경색은 뒤로가기 확인 다이얼로그와 동일한 `UiTheme.DimBackground`**
(0A0A1A, 목표 알파 166/255)로 바꿨다 — 첫 구현은 완전한 검정을 썼는데,
사용자가 "다이얼로그 배경과 동일한 색으로" 요청해서 새 색을 만들지 않고
기존 상수를 그대로 재사용했다.

**배경/텍스트를 더 이상 하나의 `CanvasGroup`으로 묶지 않는다**: 페이드아웃
구간에서 배경과 텍스트가 서로 다른 곡선(배경은 한동안 고정, 텍스트만 먼저
내려가다가 특정 지점부터 같이 내려감)을 그려야 해서, `StageClearOverlay`가
`Image`(배경)와 `TMP_Text`(텍스트)의 알파를 매 프레임 각각 계산해서 직접
설정한다(`Play()` 안의 `Mathf.Min(bgTarget, textAlpha)` 한 줄이 페이드아웃의
핵심 — bgTarget보다 큰 동안은 그대로 bgTarget, 작아지면 그 값을 그대로
따라간다). 입력 차단(`blocksRaycasts = true`)은 시각적 페이드와 무관하게
항상 켜져 있어야 해서 별도의 `CanvasGroup`(alpha 항상 1)을 Root에 하나 더
둬서 분리했다. 다른 오버레이(Toast/HintLoadingOverlay)와 다르게 입력을
막는 이유는 그대로다 — 유저가 끼어들 이유가 없는 완전 자동 전환이라, 그
사이에 곧 사라질 GameView를 조작(특히 Undo/Reset)해서 생기는 경합을 막기
위해서.

**"STAGE CLEAR"가 두 줄로 꺾이던 문제**: `FontSizeTitle`(140)을 그대로
쓰다 보니 900px 박스 안에서 줄바꿈됐다. 전용 `FontSizeStageClear`(110)로
낮추고, `TMP_Text.enableWordWrapping = false`를 명시적으로 꺼서 박스보다
넓어져도 절대 줄바꿈되지 않게 했다(마스크가 없는 텍스트라 넘쳐도 잘리지
않고 그냥 좌우로 더 넓게 그려질 뿐).

**`StageClearOverlay.Play(Handle, Func<Task> onHoldPhase)`**가 위 3구간
전체를 캡슐화한다 — `Show`/`Hide`로 만들고 없애는 것만 호출부(`GameBootstrap`)
책임이고, 타이밍 시퀀스 자체는 이제 이 클래스 안에 있다(이전 버전은
`GameBootstrap`이 `FadeTo`를 세 번 나눠 불렀는데, 배경/텍스트 알파를
따로 계산해야 해지면서 그 조립 로직 자체를 오버레이 클래스로 옮기는 게
더 자연스러웠다).

**버그: 전환되는 순간 연출이 뚝 끊겨 사라짐(2026-09-08, 사용자가 영상으로
제보)**. 원인: `onHoldPhase`(=`ShowGameAsync`)가 새 `GameView`를 만들 때
`canvas.transform`의 **맨 마지막 자식**으로 붙는 게 Unity의 기본 동작인데,
`StageClearOverlay`는 `Show()` 시점에 한 번만 `SetAsLastSibling()`을
불렀을 뿐이었다 — 그래서 전환되는 그 프레임에 새 GameView가 오버레이보다
위(=화면상 더 앞)로 올라가면서, "STAGE CLEAR"가 유지·페이드아웃 구간 내내
남아있어야 하는데 전환 순간 화면 뒤로 가려져 뚝 끊긴 것처럼 사라졌다.
**수정**: `Play()`의 2구간에서 `onHoldPhase`를 감싼 `RunHoldPhase`가 전환이
끝나는 즉시(=await 완료 직후) `overlay.Root.SetAsLastSibling()`을 다시 불러
오버레이를 최상단으로 되돌린다 — 이후 남은 유지 시간과 페이드아웃 내내
항상 최상단에 남는다.

**`GameBootstrap` 리팩터링**(이전 구현에서 그대로 유지): 기존
`ShowGame`(async void, `TitleScreen`의 Start 버튼에 그대로 꽂히는
델리게이트)의 실제 작업을 `ShowGameAsync`(async Task)로 빼고, `ShowGame`은
그걸 부르고 예외만 로그하는 얇은 래퍼로 남겼다 — `PlayStageClearThenAdvance`가
"다음 라운드가 다 준비될 때까지" `await`할 수 있어야 했기 때문(순수
`async void`는 기다릴 수 없음). `PlayStageClearThenAdvance`(async void,
`GameView.Callbacks.OnCleared`에 연결)는 라운드 번호 증가/저장 → 오버레이
표시 → `StageClearOverlay.Play(overlay, () => ShowGameAsync())` 대기 →
오버레이 제거 순서로 처리한다. `ShowGameAsync`는 `Play`의 2구간(유지) 동안
콜백으로 실행되고, `Task.WhenAll(전환 작업, Task.Delay(유지 시간))`으로
묶여 있어서 전환이 유지 시간보다 오래 걸리면(드문 경우) 유지 구간만 자연히
늘어난다.

`ShowGameAsync`는 라운드 생성이 오래 걸리면(어려운 라운드) 자체적으로
`HintLoadingOverlay`를 띄우는데(기존 기능), 클리어 직후 진입할 땐 이미
`StageClearOverlay`가 "STAGE CLEAR" 텍스트를 100% 불투명하게 띄운 유지
구간 중이라 이 스피너가 뜨더라도 화면 중앙 쪽은 거의 안 보인다. 다만 이번엔
배경 자체가 완전한 검정이 아니라 딤 다이얼로그 수준의 반투명(166/255)이라,
화면 가장자리처럼 텍스트가 덮지 않는 영역에서는 스피너가 이론적으로 살짝
비쳐 보일 수 있다 — 실제로 라운드 생성이 이 정도로 느려진 적은 없어서
지금은 방어만 해두고 넘어간다(첫 구현 때 남겨둔 한계와 동일한 결론).

**알려진 한계**: `blocksRaycasts`로 UI 클릭은 막았지만, 안드로이드
뒤로가기(Escape 키)는 `GameView.Update()`가 레이캐스트와 무관하게 직접
폴링하는 구조라 이 ~3초 전환 도중에도 여전히 반응한다 — 눌리면 "타이틀로
돌아갈까요?" 확인창이 뜬다. 실제로 이 짧은 자동 전환 도중에 뒤로가기를
누르는 경우는 거의 없을 거라 보고 지금은 막지 않았다.

## 병 선택 표시를 하이라이트 색에서 "들어올리기" 연출로 교체 (2026-09-09)

병을 탭해서 선택하면 그동안은 `BottleView`에 덧씌운 반투명 하이라이트
색(`Highlight` 오버레이 이미지)으로 표시했는데, 사용자가 스크린샷을 보고
"이 병 전체가 색으로 뒤덮이는 느낌이 별로다, 손으로 집어 든 것처럼 y축으로
살짝 떠오르게 해달라"고 요청해서 교체했다.

**`BottleView.Highlight`(오버레이 이미지) 완전히 제거**하고, 대신
`BottleView.SetLiftOffset(pixels)`를 추가했다 — `SetWaterHorizontalOffset`과
같은 패턴(`Visual`/`_waterVisual`의 offsetMin/Max를 직접 미는 것)이지만 y축만
다루고, 물 쪽에만 주는 게 아니라 `Visual`과 `_waterVisual` 둘 다 같이 밀어서
"병 전체(그림+물)가 통째로 위로 떠 있는" 모습을 만든다. 탭 히트박스인 `Root`는
건드리지 않는다 — `Root`는 `HorizontalLayoutGroup`이 위치를 관리하는 그리드
칸이라 직접 건드리면 레이아웃과 충돌한다(PourAnimator가 붓는 병을 그리드에서
떼어내는 것과 같은 이유, 위 "붓는 동안 물줄기..." 절 참고). y만 바꾸므로 붓기
스파웃 보정(`SetWaterHorizontalOffset`, x축)과는 필드가 겹치지 않아 서로
간섭하지 않는다.

**애니메이션은 `GameView`가 코루틴으로 직접 돈다**(`SetBottleLifted`/
`LiftRoutine`, `PourAnimator`처럼 `_host.StartCoroutine`을 쓰는 게 아니라
`GameView` 자신이 `MonoBehaviour`라 바로 `StartCoroutine`) — 병 인덱스별로
진행 중인 `Coroutine`을 `Dictionary<int, Coroutine>`에 들고 있다가, 재선택/
선택취소로 방향이 바뀌면 기존 코루틴을 멈추고 그 순간의 현재값(`BottleView.LiftOffset`)
에서부터 새 목표로 이어서 애니메이션한다 — 들리는 도중에 재탭해도 뚝 끊기지
않고 자연스럽게 방향만 바뀐다.

**`RefreshHighlights`(이름은 그대로 유지, 여러 곳에서 버튼 활성 상태 갱신과
같이 불림)가 `_liftedIndex`(지금 실제로 들려 있어야 할 병)와 `_selectedIndex`
(지금 선택된 병)를 비교해서 다를 때만 애니메이션을 새로 건다** — 이 함수는
선택과 무관한 이유(광고 버튼 상태 등)로도 자주 불리므로, 매번 무조건 다시
트면 이미 도착한 애니메이션을 불필요하게 재시작하게 된다. 이 한 곳의
diff-기반 처리만으로 재탭 취소·다른 병 재선택·Undo/Reset·힌트 실행(모두
`_selectedIndex = null`을 거치는 경로)이 전부 자동으로 처리된다 — 각 호출부에
따로 "들어올리기/내리기"를 챙겨줄 필요가 없다.

**딱 한 곳은 예외 — 성공한 이동으로 `PourAnimator`에 넘길 때**(`PerformMove`의
`result.Success` 분기): 애니메이션 없이 `SnapBottleLift(from, 0f)`로 즉시
0으로 스냅한다(진행 중이던 리프트 코루틴도 같이 멈춤). `PourAnimator`가 이제
막 그 병을 훨씬 큰 폭으로 스스로 들어올리는 연출을 처음부터 재생하는데,
선택-리프트의 잔여 오프셋이 그 위에 남아 있으면 그만큼 더 들뜬 것처럼
겹쳐 보인다 — 그래서 자연스러운 되돌림 코루틴 대신 즉시 스냅을 택했다.
실패한 이동(무효 이동)은 이 스냅을 타지 않고 그냥 `RefreshHighlights`의
일반 경로로 부드럽게 원래 자리로 돌아간다(사용자 확정: "옮기지 못하는 병을
누르면 다시 원래대로 부드럽게").

## 힌트 개수 경제 실제 구현 + 남은 개수 배지 UI (2026-09-09)

GameDesign.md는 진작부터(2026-08-25 확정) "힌트 무료 2회 시작, 5라운드
클리어마다 1회 충전, 최대 보유 5개"라는 규칙을 문서화해 뒀지만, 그동안
힌트 버튼은 이 규칙과 무관하게 그냥 무제한으로 눌러도 됐다(개수를 세는
코드 자체가 없었음). 사용자가 다른 게임 스크린샷을 보여주며 "힌트 버튼
우측 상단에 원형 배지로 남은 개수를 표시해달라"고 요청했는데, 표시할 실제
개수가 없었으므로 이 김에 이미 확정돼 있던 규칙 자체를 처음 구현했다(Stage
Clear 연출을 나중에서야 구현했던 것과 같은 패턴 — 문서에는 있었지만 코드는
없던 기능).

**`HintStore`(신규, `ColorSort.Managers`)**: `ProgressStore`와 완전히 같은
모양(PlayerPrefs 하나에 정수 저장) — 남은 힌트 개수만 담당한다. `LoadCount()`
(값이 아예 없으면 무료 2회로 시작), `Consume()`(힌트를 실제로 하나 쓸 때),
`AddCharge()`(충전 1회, 상한 5 클램프)만 제공하고, "몇 라운드마다"라는 주기
판단은 호출부(`GameBootstrap`)가 갖고 있는 `roundId`로 직접 계산한다 —
`HintStore`는 그 판단 결과(충전 1회)만 받아서 상한을 넘지 않게 반영하는
역할만 한다.

**충전 시점 — `GameBootstrap.PlayStageClearThenAdvance`**: `roundId++`
직후에 `if ((roundId - 1) % 3 == 0) HintStore.AddCharge();`로 계산한다
(상한 5는 `HintStore` 내부에서 클램프). 같은 날 두 번 바뀐 값이다 — 처음
구현할 땐 문서 그대로 5라운드마다 1회로 했다가, 사용자가 "매 라운드
클리어마다 1회로 바꿔달라"고 해서 무조건 충전으로 바꿨는데, 곧바로 다시
"3라운드 클리어마다 1회로 바꿔달라"고 재요청해서 지금 이 주기 계산식으로
정착했다.

**소비 시점 — `GameView.OnHintClicked`**: `HintSolver`가 실제로 다음 수를
찾았고("다음 수를 못 찾음"으로 끝나는 시도는 소비 아님) 그 출발 병이
붓는 중이 아니라서 실제로 `PerformMove`를 부르기 직전에만 `HintStore.Consume()`을
부른다 — 계산이 오래 걸리는 동안 다른 조작으로 이미 상태가 바뀌어 있을
수 있지만(입력을 안 막으므로), 그 경우도 `PerformMove` 내부의 `TryMove`
재검증이 있을 뿐 힌트 자체는 이미 유효한 수를 찾아 실행하려는 시도였으므로
정상적으로 소비 처리한다.

**힌트 버튼 비활성화**: `RefreshHighlights`의 `_hintButton.interactable`
조건에 `_hintCount > 0`을 추가했다. 0개가 되면 다 쓴 것 — 그 이후 보상형
광고로 재충전하는 흐름은 GameDesign.md에 이미 정책만 있고 아직 연동 안
했다(병 추가 버튼 때와 같은 이유로 사용자가 "나머지는 나중에 요청하겠다"고
확정한 항목, 아래 "아직 정하지 않은 것" 참고) — 그래서 지금은 그냥 버튼이
막힌다.

**배지 UI**: 새 스프라이트를 만들지 않고 기존 `UiTheme.LoadingSpinnerSprite`
(로딩 스피너와 같은 원형 그림, `Resources/Sprites/circle.png`)를 재사용했다
— 로딩 스피너 쪽은 `Image.Type.Filled`로 부채꼴만 채워 돌리지만, 배지는
`Type.Simple`로 꽉 찬 원 그대로 검은 숫자 텍스트(`UiTheme.TextOnButton`,
이미 있던 "밝은 배경 위 텍스트" 색을 그대로 재사용)를 얹는다. 힌트 버튼의
우측 상단 모서리에 중심을 살짝 안쪽으로 당겨서(`UiTheme.HintBadgeOffset`)
걸치도록 배치했다 — 정확히 모서리 중심(오프셋 0)에 두면 배지 절반이 버튼
밖으로 나가는데, 힌트 버튼 바로 오른쪽에 16px 간격으로 붙어있는 병 추가
버튼과 겹칠 수 있어서 조금 안으로 당겼다. 첫 구현은 40px/폰트 30이었는데
사용자가 "조금 더 키워달라"고 해서 같은 날 52px/폰트 36으로 키우고,
그만큼 안쪽으로 당기는 오프셋도 -10→-13으로 같이 늘렸다(크기 대비 당기는
비율은 유지 — 그래야 옆 버튼과의 간격 여유가 비슷하게 유지됨).

**꽉 찼을 때 표시 — 텍스트 "MAX"에서 배경색 변경으로 교체(같은 날 두 번째
후속 요청)**: 5개가 최대치라 그 이상 안 늘어나는데, 배지가 계속 숫자 "5"만
보여주면 유저가 그 사실을 알 방법이 없다는 지적을 받아, 처음엔 숫자 대신
`"MAX"` 텍스트를 넣는 방식으로 구현했다(그러려고 TMP `enableAutoSizing`도
켰었음 — 3글자가 숫자 한 글자용 폰트 크기로는 원 밖으로 넘쳐서). 그런데
사용자가 실제로 보고 "MAX 텍스트가 좁은 원 안이라 잘 안 보인다"고 해서,
텍스트는 그대로 숫자만 보여주고 **배경색이 흰색(`HintBadgeNormalColor`)에서
노란색(`HintBadgeFullColor`)으로 바뀌는 방식**으로 다시 교체했다 — 색 변경이
좁은 배지 안에서 훨씬 잘 보이고, 숫자("5")도 계속 그대로 읽혀서 "몇 개가
꽉 찬 상태인지"까지 알 수 있다는 장점도 있다. 자동 크기 조절 관련 코드
(`enableAutoSizing`/`enableWordWrapping`/`HintBadgeFontSizeMin`)는 더 이상
필요 없어져서(항상 숫자 한 글자만 표시) 전부 되돌렸다.

**힌트 충전 시 "+1" 플로팅 텍스트(같은 날 세 번째 후속 요청)**: 3라운드마다
힌트가 조용히 1개씩 늘어나는데, 배지 숫자가 슬쩍 바뀌는 것만으로는 "방금
충전됐다"는 게 잘 안 느껴진다는 요청으로 추가했다. `FloatingHintCharge`
(신규, `ColorSort.UI`) — Toast와 같은 "코루틴 붙인 컴포넌트가 재생 후 자기
자신을 파괴" 패턴이지만, Toast는 항상 화면 중앙 고정인 반면 이건 배지
(임의 UI 요소) 바로 위에서 시작해야 해서 시작 좌표를 매번 계산한다 —
`PourAnimator.ToLocal`/`UpdateStream`이 물줄기 시작점을 구할 때 쓰던 것과
똑같은 "월드 좌표 → 스크린 좌표 → 대상 RectTransform 기준 로컬 좌표" 변환을
그대로 재사용했다(이미 이 프로젝트에서 검증된 방식). 연출 자체는 사용자
확정 그대로: 페이드인 없이 즉시 "+1" 등장 → 위로 떠오르면서(`RiseDistance`)
동시에 투명해지다가(`CanvasGroup.alpha`) 사라짐, 별도 유지 구간 없음(Toast와
다른 점 — Toast는 등장/유지/퇴장 3단계, 이건 등장 즉시 + 단일 상승-페이드
단계뿐).

첫 구현은 배지(버튼 오른쪽 위 모서리)를 기준 좌표로 삼고 색도 배지와 같은
노란색(`HintBadgeFullColor`)을 재사용했는데, 사용자가 실제로 보고 "위치가
너무 오른쪽으로 치우쳤다, 힌트 버튼 위에 뜨게 해달라"고 해서 기준 대상을
배지(`_hintBadgeImage`)에서 힌트 버튼 자체(`_hintButton`)로 바꿨다 —
`FloatingHintCharge.Show`는 넘겨받은 RectTransform의 위쪽 모서리 중앙에서
시작하므로, 버튼 전체를 기준으로 삼으면 자연히 버튼 가로 중앙 위에서
뜬다. 색은 같은 피드백에서 "노란색 대신 흰색으로"도 같이 요청받아
`UiTheme.TextPrimary`로 바꿨다.

**시작 높이 재조정(같은 날 네 번째 후속 요청)**: 버튼 위쪽 모서리에 딱
붙어서 시작하니 배지랑 너무 가까워 보인다고, 사용자가 참고 스크린샷에
빨간 박스로 원하는 시작 지점(버튼보다 확연히 위)을 표시해서 보내왔다.
`FloatingHintCharge.Show`가 버튼 위쪽 중앙 좌표(`buttonTopCenter`)를 구한
뒤 `UiTheme.FloatingHintChargeStartExtraRiseY`(60px)만큼 더 위로 올린
지점을 실제 시작 위치(`startPos`)로 쓰도록 바꿨다. 시작점이 이미 높아진
만큼, 사용자가 "떠오르는 높이는 조금만 더 짧게"라고 같이 요청해서
`FloatingHintChargeRiseDistance`도 70→50으로 줄였다.

**트리거 시점과 "실제로 늘었을 때만" 가드**: 충전은 `GameBootstrap.
PlayStageClearThenAdvance`에서 일어나지만, 힌트 버튼(이 애니메이션을 붙일
대상)은 다음 라운드의 새 `GameView`가 만들어져야 존재한다 — 그래서
`GameView.Build`/`Initialize`에 `showHintChargeAnimation` 플래그를 추가로
흘려보내고, `BuildBottomBar`로 버튼을 만든 직후에 `FloatingHintCharge.Show`를
부른다. 또한 이미 최대치(5개)일 때 3라운드 주기가 마침 겹치면
`HintStore.AddCharge()`를 불러도 실제로는 개수가 안 늘어나는데(내부에서
상한 클램프), 이 경우까지 "+1"을 띄우면 거짓 정보라 — `PlayStageClearThenAdvance`가
`AddCharge()` 전후 값을 비교해서 실제로 늘었을 때만 플래그를 true로 넘긴다.

**버그 — x좌표가 버튼 중앙이 아니라 다른 자리에서 시작함(같은 날 다섯 번째
후속 요청, 사용자가 직접 실행해보고 발견)**: `BuildBottomBar`가 `_hintButton`을
막 만든 그 직후에 곧바로 `GetWorldCorners`로 위치를 읽었는데, `rightGroup`의
`HorizontalLayoutGroup`이 버튼들의 실제 위치(anchoredPosition)를 계산하는
레이아웃 재계산은 Unity가 즉시 처리하지 않고 프레임 끝에 한 번 모아서
처리한다 — 그래서 그 자리에서 바로 읽은 좌표는 아직 레이아웃이 반영되기
전(엉뚱한 위치)이었다. `RebuildBottles`가 병 배치 직후 `FillArea.rect.height`를
읽기 전에 `Canvas.ForceUpdateCanvases()`로 레이아웃을 강제로 먼저 끝내는
것과 정확히 같은 종류의 버그(이 프로젝트에서 이미 한 번 겪었던 패턴) —
같은 처방으로 `FloatingHintCharge.Show`를 부르기 직전에
`Canvas.ForceUpdateCanvases()`를 추가해서 고쳤다.

## STAGE CLEAR 텍스트 뒤 원형 파티클 축하 이펙트 (2026-09-09)

사용자가 "Stage Clear 애니메이션 뒤 백그라운드에 원형으로 팡 터지는 효과를
추가해달라"고 요청했다. 새 파티클 시스템(Unity `ParticleSystem`)을 쓰지
않고, 이 프로젝트가 지금까지 모든 연출(붓기 물줄기, 플로팅 텍스트 등)을
해온 방식 그대로 — 이미 있는 원형 그림(`circle.png`, 로딩 스피너·힌트
배지와 같은 에셋)을 여러 개 복제해서 각자 다른 각도로 동시에 밀어내는
방식으로 만들었다(`StageClearBurst`, 신규).

**z-order — Background와 Text 사이**: "뒤에 백그라운드에"라는 표현대로
파티클이 텍스트보다는 아래, 딤 배경보다는 위에 있어야 한다. `StageClearOverlay.Show`가
`Background`를 만든 직후, `Text`를 만들기 전에 빈 `Burst` 컨테이너를 만들어
둬서 형제 순서(z-order)를 미리 고정해 놓는다(`Handle.BurstLayer`).

**타이밍 — 텍스트가 다 나타난 뒤가 아니라 나타나는 도중(재확정, 같은 날
후속 요청)**: 처음엔 텍스트가 100% 불투명해지는 순간(1구간→2구간 전환
시점, 페이드인 종료)에 맞춰 틀었는데, 사용자가 "텍스트가 완전히 나타나는
순간 말고 나타나고 있는 도중(페이드인 0~0.5초 지점)에 재생됐으면 좋겠다,
지금보다 0.5초 더 빠르게"라고 재요청해서 페이드인 절반 지점(0.5초)으로
당겼다. `Play()`의 1구간(페이드인) `Animate` 콜백 안에서 진행률 `t`가
처음으로 0.5 이상이 되는 프레임에 `StageClearBurst.Play`를 딱 한 번만
부르는 식으로 구현했다(`burstStarted` 플래그로 중복 실행 방지) — `t`가
0~1 진행률이고 `StageClearFadeInTime`이 1초라 `t>=0.5`가 정확히 실제
경과 0.5초와 같다. 프레임이 유난히 크게 걸려 0.5 지점을 건너뛰는 극단적
경우를 대비해, `Animate`가 끝난 뒤에도 아직 안 텄으면 한 번 더 방어적으로
튼다.

**구현**: `StageClearBurst.Play(RectTransform layer)`가 파티클
`UiTheme.StageClearBurstParticleCount`(14)개를 원 중심(0,0)에 겹쳐서 만들고,
각각 `360°/개수`씩 다른 각도의 단위 방향 벡터를 미리 계산해 둔다. 파티클
개별로 컴포넌트를 붙이는 대신(Toast/FloatingHintCharge와 다른 점) `Burst`
컨테이너 하나에만 `Runner`(코루틴)를 붙여서, 그 코루틴 하나가 매 프레임
배열을 순회하며 전체 파티클의 위치(`방향 × 거리`, ease-out cubic으로
빠르게 튀어나갔다 감속)와 알파(퍼지는 동안 1→0으로 선형 감소)를 한 번에
갱신한다 — 파티클 수만큼 코루틴을 따로 두는 것보다 저렴하다. 재생이
끝나면 파티클들과 `Runner` 자신을 정리하지만, `Burst` 컨테이너(부모)
자체는 안 건드린다 — 오버레이 전체가 몇 초 더 살아있다가 `StageClearOverlay.Hide`가
한꺼번에 정리한다.

**색**: 새 색을 만들지 않고 `UiTheme.PrimaryColor`(앱 전체에서 이미 쓰는
청록색 포인트 컬러)를 그대로 재사용했다 — 물병 색상 팔레트(`WaterPalette`)는
게임 콘텐츠(물 색) 전용이라 장식 이펙트에 끌어다 쓰지 않는다는 원칙을
유지했다.

**병 완성 시 축소판 버스트 (2026-09-10)**: "물병 하나를 같은 색으로 다
채웠으면 그 병에서 조그맣게 이펙트를 내달라(스테이지 클리어처럼)"는 요청으로
`BottleCompleteBurst`(신규)를 추가했다 — 재생 로직은 `StageClearBurst`와
동일(circle.png 여러 개를 방사형으로 밀며 옅어짐)하고 `UiTheme.BottleCompleteBurst*`로
파티클 수 8·크기 16·거리 90·시간 0.5s로 줄인 축소판. `StageClearBurst`가
오버레이가 만들어 둔 중앙 layer를 빌려 쓰는 것과 달리, 병마다 위치가
달라서 자기 컨테이너를 만들어 월드 좌표(완성된 병 `Root` 중앙)에 놓고 다
끝나면 그 컨테이너째 스스로 파괴한다. `GameView.PerformMove`에서 성공한
이동의 도착 병이 `IsFullyStacked`(가득 + 단색 + 비어있지 않음)면
`PourLiftTime + PourFlowTime`만큼(붓기로 물이 다 차오르는 시점) 기다렸다
재생하는 코루틴을 건다 — 기다리는 사이 Undo/Reset으로 완성이 풀렸으면
발사 직전에 다시 확인해서 취소한다. 도착 병은 붓기 전 `IsFull`이면 애초에
부을 수 없으니, 이동 직후 가득 찼다면 방금 그 이동으로 완성된 것이라
"이번에 새로 완성" 판정은 이 한 줄로 충분하다.

**위치·색 조정 (2026-09-10, 같은 날)**: 처음엔 병 정중앙(`Root.position`)에서
파란색(PrimaryColor) 고정으로 터뜨렸는데, (1) 위치를 병 윗변 중앙으로 올리고
(`Root.GetWorldCorners`의 TL·TR 평균), 인게임에서 보며 맞추라고
`UiSkin.BottleCompleteBurstOffset`(Vector2, 디자인 픽셀 → `lossyScale` 곱해
캔버스 배율 반영)로 시작 위치 미세조정을 Inspector에 뺐다. (2) 색을
`UiTheme` 상수 대신 그 병을 채운 물 색(`WaterPalette.Get(container.TopColor)`)을
`BottleCompleteBurst.Play(parent, worldCenter, color)` 인자로 넘겨서, 완성한
색과 이펙트 색 계열이 같아지게 했다.

## 물이 밋밋해 보이는 문제 — 재도전, 이번엔 코드로 생성한 그라디언트 (2026-09-09)

사용자가 다른 게임 스크린샷(진짜 유리 플라스크처럼 빛이 반사되는 느낌)과
다시 비교하며 "그냥 2D 네모에 색칠만 해놓은 느낌"이라고 재차 지적했다.
같은 문제 제기가 2026-09-08에도 한 번 있었고(위 "물이 밋밋해 보이는 문제"
절 참고), 그때 `UiSkin.BottleHighlight`에 AI가 생성한 정적 이미지
(`glass_highlight.png`)를 연결해 봤다가 "그냥 별로"라는 피드백으로 기능
자체를 롤백한 전적이 있다 — **레이어 순서(물 위, 병 그림 아래) 진단은
맞았지만, 그림 자체의 품질이 문제였다.**

이번엔 같은 레이어 순서 전략을 그대로 쓰되, **외부 이미지 품질에 기대지
않기 위해 하이라이트를 그림 파일이 아니라 코드로 직접 생성**했다 —
`UiTheme.GlassHighlightSprite`가 런타임에 1×64픽셀 가로 그라디언트
`Texture2D`를 만들어(부드러운 종 모양 알파, `smoothstep`) `Sprite`로
변환하고, 한 번 만든 뒤엔 캐시해서 재사용한다. 위치(`GlassHighlightPeakX`,
왼쪽에서 28% 지점 — 참고 이미지의 빛줄기 위치)·퍼짐 정도
(`GlassHighlightSoftness`)·최대 밝기(`GlassHighlightMaxAlpha`)를 전부
상수로 뒀다. 이 방식의 장점은 그림 파일을 다시 만들 필요 없이(이전
실패의 원인이었던 "AI 생성 이미지가 이상해 보임" 문제 자체를 우회) 값
몇 개만 조절해서 바로 다른 느낌을 시험해 볼 수 있다는 것 — 실제로 바로
다음 피드백("느낌 괜찮은데, 살짝 너무 밝다")에서 그 장점이 그대로
증명됐다: `GlassHighlightMaxAlpha`를 0.3→0.22로 낮추는 것만으로 끝났다
(그림이었다면 다시 그려야 했을 조정).

`BottleView` 생성자에서 `FillArea`를 만든 직후(형제, `FillArea`보다 나중에
= z-order상 더 위)에 이 스프라이트를 얹는다 — `FillArea`와 완전히 같은
anchor를 써서 마스크가 실제로 물을 보여주는 영역과 정확히 겹치고
(`BottleMask`가 있으면 같은 `Mask` 안이라 실루엣 밖으로 안 튀어나옴),
물 세그먼트가 몇 개든 색이 뭐든 상관없이 항상 그 위로 한 줄기 빛이 세로로
가로지르는 것처럼 보인다 — 참고 이미지에서 병마다 색이 달라도 빛줄기
위치는 항상 같은 것과 같은 원리(2026-09-08 첫 시도 때와 동일한 통찰,
`docs/Sprites.md`에도 이미 남아있던 원리를 이번엔 그림 없이 코드로
구현했다는 차이).

물 세그먼트 자체(색이 채워지는 사각형)에 원통형 명암(왼쪽 밝게·오른쪽
어둡게 등)을 추가로 넣는 건 이번엔 하지 않았다 — 하이라이트 하나만으로
얼마나 나아 보이는지 먼저 확인한 뒤, 필요하면 같은 절차(코드 생성
그라디언트)로 추가하는 게 리스크가 적다고 판단했다(이전 실패 이후로
"한 번에 다 바꾸지 말고 반응을 보고 다음 걸 더하자"는 방향).

이 하이라이트는 사용자가 "느낌 괜찮다"고 확인했고, 최대 밝기만 0.3→0.22로
살짝 낮췄다(같은 날 후속 피드백 "살짝 눈에 너무 밝다").

## 붓는 병이 기울 때 물이 유리처럼 뻣뻣하게 도는 문제 — 액체 전단(shear) 효과 (2026-09-09)

사용자가 다른 게임 스크린샷과 자기 게임 스크린샷을 나란히 비교하며 지적했다:
"물병 안에 있는 물들도 같이 어느정도 기울여져 보여야하는데, 물병에 물이
그대로 부착되어 있는 느낌으로 되있어서 사각형 그대로 물병 바닥에 붙어있어.
그래서 물병의 윗부분에서 물이 흐르는데 그 안에 내용물이 무슨 포탈을 통해서
물이 나오는 것 처럼 보여지고있어."

**진단**: 코드상으로는 물(`FillArea`와 그 자손 세그먼트들)이 `_waterVisual`
(`WaterMaskRoot`) 안에 있어서 `SetTilt`가 걸릴 때 병 그림(`Visual`)과 정확히
같은 각도로 이미 회전하고 있었다 — 즉 "안 돌고 있다"는 게 아니라, **강체로
통째로 돌기만 해서 액체처럼 안 보였다**는 게 진짜 문제였다. 세그먼트 색
경계선(그리고 맨 위 수면)이 사각형의 위/아래 변, 즉 병의 긴 축에 항상 수직인
직선이라, 병이 65도로 기울면 그 직선도 같이 65도 기울어진 채로 통째로
회전한다 — 실제 액체라면 중력 때문에 표면이 그보다 훨씬 수평에 가깝게
남아있어야 하는데, 이 프로젝트의 물은 "회전한 딱딱한 블록"처럼 보였다.
사용자가 말한 "포탈"은 이 뻣뻣함 때문에 물이 흘러나오는 지점과 물 내용물의
실제 모양이 안 어울려 보이는 것이었다.

**시도 — LiquidShearEffect, 실제로 보니 롤백함(같은 날)**: RectTransform은
회전/스케일만 되고 전단(shear)은 지원하지 않아서, 그래픽 메시의 정점을
직접 미는 `BaseMeshEffect`를 만들어 봤다. 세그먼트 하나의 로컬 y(0~자기
높이)에 그 세그먼트가 물기둥 전체에서 몇 px 높이에서 시작하는지
(`BaseHeightPixels`, `ApplySegmentUnitCount`가 이미 계산해 두던 `baseHeight`를
재사용)를 더해 "물기둥 전체 기준 절대 높이"를 구하고, 그 절대 높이에
비례해서(`ShearPerPixel`, 기울기에 선형 비례 — 65도 같은 큰 각도에서 값이
급격히 커지는 tan() 기반 계산은 피함) x축으로 정점을 미는 방식이었다 —
병 바닥은 거의 안 밀리고 수면에 가까울수록 더 많이 밀리게.

사용자가 실제로 인게임으로 확인한 결과 "굉장히 이상한데.. 뭐 기울여지지도
않은 것 같고 물병밖으로 물이 튀어나와있고"라는 반응이었다 — **바로
롤백했다**: `LiquidShearEffect.cs` 삭제, `BottleView`의 `Segment.Shear`
필드/`CreateSegment`의 컴포넌트 부착/`ApplySegmentUnitCount`의
`BaseHeightPixels` 갱신/`SetTilt`의 전단 계산을 전부 제거, `UiTheme.PourLiquidShearMaxPerPixel`
상수도 제거 — 위 SetTilt는 순수 회전만 하던 원래 상태로 되돌아갔다.

**왜 실패했는지(정확한 원인은 에디터로 직접 확인 못 해서 미확정)**: 코드
리뷰만으로는 다음 후보들을 배제 못 했다 — (1) 부호/크기 계산을 소각도
근사로 유도했는데 실제 65도 같은 큰 각도에서 근사가 무너졌을 가능성,
(2) `Mask`(스텐실 클리핑)가 `BaseMeshEffect`로 정점이 밀린 메시에도
정상적으로 적용되는지 실제로 검증하지 못한 채 "이론적으로는 되어야 한다"고
가정했는데 그 가정이 틀렸을 가능성. 이 프로젝트는 에디터를 직접 실행해서
눈으로 확인할 수 없는 환경(사용자만 실행 가능)이라, 이런 종류의 "메시를
직접 조작하는" 실험적 시도는 실패 시 되돌리는 비용이 크다는 교훈이 남았다
— 이 물병 하이라이트 배지(위 절)처럼 값 몇 개만 조절하면 되는 방식이
아니라 애초에 접근 자체가 틀렸을 수 있는 방식이라 더 위험했다. 물이
"뻣뻣해 보인다"는 원래 지적 자체는 여전히 유효한 진단으로 남겨두되, 다음에
다시 시도한다면 사용자가 Unity 에디터에서 직접 파라미터를 바꿔가며 눈으로
확인할 수 있는 형태(예: Scene 뷰에서 슬라이더로 조절 가능한 디버그 값)로
접근하는 게 더 안전할 것 같다.

**재시도, 그리고 다시 롤백 — LiquidTiltEffect(2026-09-09, 같은 날 재요청)**: 사용자가 다른
게임 스크린샷·포토샵으로 직접 편집한 목업 이미지까지 첨부하며 다시
요청했다: "그냥 물병이 기울어진만큼 제일 아래는 삼각형 모양에, 그 위로는
사다리꼴 모양으로 변경되게 하면 될 것 같은데." 다시 시도할지 물어봤고
사용자가 "그래도 다시 시도해줘"를 선택했다.

이전 시도(`LiquidShearEffect`)의 근본적인 결함을 짚었다: 그건 "절대 높이가
클수록 모든 정점(왼쪽·오른쪽 상관없이)을 같은 방향으로 옆으로" 밀었다 —
그러면 위/아래 변의 길이가 그대로 보존돼서 사각형이 옆으로 밀린
**평행사변형**만 나올 수 있고, 애초에 삼각형/사다리꼴(위아래 변 길이가
서로 다른 도형)은 이 방식으로는 표현 자체가 불가능했다 — 방향/크기를
아무리 잘 골랐어도 원천적으로 틀린 접근이었다.

`LiquidTiltEffect`(신규)는 대신 **왼쪽 벽과 오른쪽 벽에서 서로 반대
방향으로 정점을 "세로로"** 민다(`Δy = slope × (x - 폭/2)` — x가 왼쪽
벽(0)에 가까우면 음수 방향, 오른쪽 벽에 가까우면 양수 방향으로 부호가
갈림). 이러면 색 경계선 자체가 대각선이 되고, 서로 다른 절대 높이의
경계선은 기울기(`slope`)가 다르므로 위/아래 변의 길이가 달라지는 진짜
사다리꼴이 나온다. 인접한 두 세그먼트의 맞닿는 변(한쪽의 top, 다른 쪽의
bottom)은 정확히 같은 절대 높이 값을 참조해 계산되므로 층 사이에 끊김이
없다. 맨 아래층이 "삼각형처럼" 보이는 부분은 별도로 계산하지 않았다 —
이 사다리꼴이 병의 둥근 바닥 실루엣(`BottleMask`)에 의해 한쪽 모서리가
잘려나가면서 기존 마스크 클리핑이 자연스럽게 만들어 줄 것으로 기대한다.

이전 실패에서 얻은 교훈대로 이번엔 크게 두 가지를 다르게 했다:
1. **기하학적으로 다른(더 올바른) 메커니즘**(옆으로 미는 평행사변형 →
   벽마다 반대 방향으로 세로로 미는 사다리꼴)을 썼다 — 이전 것을 그대로
   두고 값만 조절하는 게 아니라 접근 자체를 바꿨다.
2. **처음부터 보수적인 크기**(`PourLiquidTiltSlopePerPixel = 0.001`, 최대
   기울었을 때도 모서리 이동량이 세그먼트 반폭 대비 크게 튀지 않는 수준)로
   시작했다 — 과하게 잡았다가 또 "이상하다"는 반응이 나오는 것보다, 약하게
   시작해서 "더 티나게" 요청받는 실패 모드가 훨씬 안전하다고 판단했다.

X축 이동이 없어서(세그먼트의 왼쪽/오른쪽 경계 자체는 항상 원래 폭[0, width]
안에 머무름) 물이 마스크 실루엣 밖으로 튀어나오는 이전 문제의 원인(X 방향
이동이 회전과 결합해 마스크 경계를 넘어갔을 가능성)도 구조적으로 줄었다.

**하지만 사용자가 확인해보지도 않고 바로 "일단 원래대로 돌려줘. 너가 지금
너무 어렵게 생각하는 것 같은데"라고 롤백을 요청했다** — 두 번째 시도가
기하학적으로 더 올바른 방향이었다는 것과 별개로, 코드로만 계속 정교하게
다듬어 가는 접근 자체에 대한 신뢰를 잃은 것으로 보인다. `LiquidTiltEffect.cs`
삭제, `BottleView`/`UiTheme`를 `git checkout`으로 커밋된 상태(글라스
하이라이트만 있던 상태)로 되돌렸다 — 두 번의 시도(`LiquidShearEffect`,
`LiquidTiltEffect`) 모두 최종적으로는 코드에 남아있지 않다.

**남은 결론**: "붓는 병이 기울 때 물이 뻣뻣해 보인다"는 지적 자체는
유효하지만, 이 프로젝트 환경(에디터를 직접 실행해서 눈으로 확인할 수
없음)에서 메시 정점을 직접 계산하는 방식으로 두 번 시도해 두 번 다 만족스럽지
않았다 — 세 번째로 다시 시도한다면 사용자가 먼저 "이 정도까진 괜찮다"고
느끼는 기준선을 스크린샷/목업으로 더 구체적으로 잡아주거나, 코드가 아닌
다른 경로(실제 아트 에셋 제작, 또는 사용자가 Unity에서 직접 파라미터를
조절하며 확인하는 형태)를 우선 고려하는 게 나을 것 같다.

## 세 번째 시도 — WaterBands(수평 밴드 컨테이너), 사용자가 직접 알고리즘을 제시 (2026-09-09)

바로 이어서 사용자가 그림 3장(현재 상태·참고 게임·포토샵으로 직접 편집한
목업, 특히 세 번째엔 "기울어진 물 영역의 세로 높이"를 빨간 기역자로 표시)을
첨부하며 훨씬 구체적인 스펙과 함께 알고리즘까지 직접 제시했다: "기울였을
때의 물병의 높이를 구하고, 물의 색 개수만큼 나누면 칸 하나의 높이가 나온다.
물병 안에 물이 색칠되는 범위는 bottle_mask 이미지 생긴대로다 — 나눈 범위만큼
색을 보여주면 끝 아니냐"고 재차 확인했다.

이 설명을 듣고서야 이전 두 시도가 **잘못된 문제를 풀고 있었다**는 걸
깨달았다 — 정점을 옆으로 밀거나 위아래로 어긋나게 미는 방식(전단/사다리꼴
메시)은 "이미 회전한 사각형 하나를 왜곡"하는 접근인데, 사용자가 원하는 건
그게 아니라 **"물 내용물 자체는 회전시키지 말고 수평을 유지한 채로, 이미
검증된 기존 BottleMask 클리핑이 알아서 보이는 모양을 잘라내게 두는"**
훨씬 단순한 접근이었다. "bottle_mask 이미지 생긴대로"라는 표현이 핵심 —
정확한 교차점을 직접 계산할 필요 없이, 이미 완벽하게 동작하는 마스크에게
그 일을 맡기면 된다는 뜻이었다.

**구현 — `_waterBands`**: `WaterMaskRoot`(마스크, 계속 회전) 밑에 새 컨테이너를
하나 두되, 이 컨테이너는 <b>부모 회전을 매 프레임 반대로 되돌려서(`SetTilt`가
`-degrees`를 걸어줌) 항상 수평을 유지</b>한다. 핵심은 이 컨테이너의 회전
중심(pivot)을 `WaterMaskRoot`의 회전 중심과 **정확히 같은 점에 앵커**해 둔
것 — 그러면 반대로 되돌리는 회전이 부모의 회전을 상쇄만 할 뿐 위치는 전혀
안 밀린다(이전 두 시도에서 고민했던 "회전 중심이 어긋나면 위치가 같이
밀린다"는 문제를 별도 보정 계산 없이 앵커 설정 하나로 해결). 크기는
어떤 각도로 기울어도 마스크 실루엣을 다 덮을 만큼 넉넉하게(병 높이의 2.2배
정사각형) 잡아서, "정확한 폭 계산" 자체를 필요 없게 만들었다 — 넘치는 부분은
기존 `Mask` 컴포넌트가 알아서 잘라낸다.

**세그먼트 배치 — `RelayoutSegments`(신규)**: `FillArea`의 네 모서리를
(마스크 회전 중심 기준 오프셋으로) 생성 시점에 한 번 구해 두고, 매번
현재 기울기만큼 실제로 회전시켜서 "지금 화면에 보이는 기울어진 물 영역의
세로 범위(최소~최대 y)"를 구한다 — 사용자가 "기울였을 때의 높이"라고 표현한
바로 그 값. 이 범위를 세그먼트별 비율(`UnitCount / Capacity`)로 나눠서 각
세그먼트를 그냥 수평 사각형으로 배치하면 끝 — 삼각형/사다리꼴 모양은 이
사각형이 마스크에 잘려나가면서 자연스럽게 나온다(직접 계산 안 함). 세그먼트
하나의 높이가 바뀌면 그 위에 쌓인 세그먼트들의 시작 위치도 같이 밀리므로,
`ApplySegmentUnitCount`(유닛 수가 바뀔 때)와 `SetTilt`(기울기가 바뀔 때)
둘 다 전체를 다시 배치한다.

**기존 로직과의 분리**: `FillArea` 자신은 전혀 안 건드렸다 — 여전히
`WaterMaskRoot`와 같이 회전하고, `WaterSurfaceWorldPosition`/`PourAnimator.SpoutWorldPosition`
등 물줄기 정렬에 쓰이는 기존 좌표 계산은 그대로 `FillArea`를 참조해서
전혀 영향받지 않는다(이 부분은 이미 여러 번 다듬어 고쳐 놓은 안정적인
로직이라 건드릴 이유가 없었다) — `_waterBands`는 순수하게 "무엇이 보이는지"만
바꾸는 새 레이어이고, "어디서 물줄기가 시작되는지" 계산과는 완전히 분리돼
있다. `BottleMask`가 없는 폴백 상황(스프라이트 미설정)에서는 `_waterBands`
자체가 안 만들어지므로 예전 방식(병의 긴 축 기준으로 쌓기) 그대로 동작한다.

이번에도 에디터에서 직접 확인은 못 했지만, 이전 두 번과 달리 사용자가 직접
제시한 알고리즘을 그대로 구현했고, 기존에 이미 검증된 마스크 클리핑에게
어려운 부분(정확한 교차점 계산)을 떠넘기는 구조라 실패 지점이 훨씬 적다.

**버그 — 안 기울었을 때 물 크기가 커져 보임(같은 날 바로 발견)**: 붓는 중
기울어진 모습은 괜찮았는데, 평소(안 기울었을 때) 물이 병 밖으로 삐져나올
만큼 커 보인다는 피드백을 받았다. 원인은 `RelayoutSegments`가 "기울었을
때의 높이"를 구하려고 `FillArea`의 네 모서리를 **상수(`UiTheme.BottleWidth/BottleHeight`)
기반으로 미리 계산**해 두고 매번 그 값을 돌리는 방식이었는데, 안 기울었을
때(회전 0도) 이 계산 결과가 이론상으로는 살아있는 `FillArea.rect.height`
(예전부터 쓰던, 검증된 값)와 같아야 하는데도 실제로는 미묘하게 달랐다 —
정확한 불일치 원인을 코드 리뷰만으로 못 찾았다(레이아웃 타이밍, 부동소수
오차 등 여러 후보가 있었지만 특정 못 함).

원인을 정확히 찾는 대신, 사용자가 애초에 요청한 방향("물들의 사이즈는
기본적으로 원래대로 해주고 물병이 기울여졌을 때만 유지") 그대로 **더 안전한
방식으로 통째로 교체**했다: 상수 기반으로 미리 계산해 둔 모서리 대신,
`FillArea.GetWorldCorners()`로 **매번 실제 월드 좌표를 직접 측정**해서
`_waterBands` 기준 로컬 좌표로 변환하는 방식으로 바꿨다(`Transform.InverseTransformPoint`
사용) — 이건 `PourAnimator`가 물줄기 시작점을 구할 때 이미 쓰고 있는
"측정" 패턴과 같아서, 상수와 라이브 값 사이에 어떤 오차가 있었든 근본적으로
사라진다(안 기울었을 때든 기울었을 때든 항상 같은 방식으로, 항상 실제
현재 상태를 그대로 측정하므로). 미리 계산해 두던 `_fillAreaCornersLocal`
필드와 `_currentTiltDegrees` 필드는 더 이상 필요 없어져서 제거했다.

**두 번째 버그 — 안 기울었을 때 물이 옆으로 삐져나옴(같은 날, 사용자가
유니티 에디터 Hierarchy를 직접 열어서 진단)**: 위 수정으로 세로(높이)는
해결됐는데, 이번엔 물이 좌우로 병 밖까지 삐져나왔다. 사용자가 직접
Hierarchy를 열어서 원인을 짚어줬다: `WaterMaskRoot`는 병 전체 크기
(`BottleWidth`)만큼인데, 세그먼트가 그 폭 전체로 가로 스트레치돼 있어서
(`_waterBands`가 넉넉하게 잡은 정사각형 폭에 맞춰 꽉 채우던 방식) 물이
`FillArea`의 실제(트리밍된, 더 좁은) 폭보다 넓게 그려졌다 — "물은
FillArea의 사이즈에 맞게 해야 한다"는 사용자 진단이 정확했다.

**수정**: 세그먼트를 더 이상 `_waterBands` 폭에 맞춰 스트레치하지 않고,
세로와 완전히 같은 방식(`RelayoutSegments`가 `FillArea.GetWorldCorners()`로
직접 측정)으로 **가로 범위도 매번 실측**해서 폭·중심을 명시적으로 넣는다 —
세그먼트 앵커를 스트레치에서 점 앵커(`_waterBands` 중심 기준)로 바꾸고
`sizeDelta.x`/`anchoredPosition.x`를 `RelayoutSegments`가 직접 계산해서
채운다. `_waterBands` 자체의 크기는 이제 세그먼트 렌더링에 전혀 영향을
안 준다(그냥 빈 컨테이너 역할만).

**세 번째 버그 — 이번엔 기울였을 때 다시 커짐**: 안 기울었을 때는 고쳤는데,
기울이자 또 물이 병보다 커 보인다는 피드백을 받았다. 원인은 두 번째
수정에서 쓴 "FillArea의 회전된 네 모서리의 최소~최대 범위(바운딩 박스)"
계산 자체에 있었다 — **좁고 긴 사각형을 기울이면, 그 바운딩 박스(가로/세로
축에 나란한 최소 감싸는 사각형)는 대각선 길이 때문에 원래 폭보다 훨씬
넓어진다.** 안 기울었을 때(0도)는 우연히 바운딩 박스 폭이 실제 폭과
일치해서 문제가 안 보였을 뿐, 기울이는 순간 이 계산 자체가 근본적으로
틀린 값을 내고 있었다.

**수정(4번째)**: 폭을 바운딩 박스에서 구하는 대신, 항상 `FillArea.rect.width`
(회전과 무관하게 항상 일정한, 병의 진짜 폭)를 그대로 쓴다. 위치는 FillArea의
바닥 중심과 입구 중심을 실측해서 잇는 선분("병이 기운 방향의 중심축")을
세그먼트 비율만큼 나눠 그 구간의 중점에 배치한다.

**결과 — 더 심하게 망가짐, 전체 롤백**: 실제로 보니 오히려 훨씬 이상해졌다
(작은 색 조각들이 서로 안 이어진 채 흩어져 보임). 되짚어 보면 이 4번째
수정도 여전히 틀린 접근이었다 — "병의 진짜 폭"(병의 긴 축에 수직인 방향의
폭)을 화면상 그냥 가로(수평) 방향 크기로 그대로 썼는데, 병이 크게
기울어진 상태에서는 "긴 축에 수직인 방향"과 "화면상 수평 방향"이 전혀
다른 방향이라 이 값 자체가 의미가 없었다. 즉 네 번의 시도 전부 — 정점을
미는 방식이든, 축을 따라가는 방식이든 — 회전한 좁고 긴 도형을 다루는
기하학을 매번 다른 지점에서 잘못 짚었다.

사용자가 "그냥 물이 차 있는 공간을 WaterMaskRoot 크기가 아니라 FillArea
크기로 바꾸려던 것뿐인데 왜 이렇게 됐냐"고 정확히 지적했다 — 맞는 지적이다.
간단해 보이는 요구였지만 "기울어진 상태에서 색 경계가 수평을 유지"라는
조건과 결합되는 순간 실제로는 회전 기하학이 얽힌 문제가 됐고, 그걸 코드만
보고(에디터에서 직접 눈으로 확인 못 하는 채로) 네 번 다 정확히 못 맞췄다.

**전체 롤백 → 사용자 요청으로 특정 체크포인트만 복구**: 처음엔 `BottleView.cs`를
이 기능을 시작하기 전 마지막 커밋(`96ce3de`, 유리 하이라이트만 있던 상태)으로
`git checkout`해서 완전히 되돌렸다. 하지만 사용자가 "전전 상태(안 기울었을
때 사이즈는 정확했던 버전)가 원하던 느낌에 거의 근접했었는데 왜 되돌렸냐"고
되물었다 — 여러 중간 상태를 오가며 고치다 보니 "지금 상태"에 대한 이해가
서로 어긋났던 것. 커밋되지 않은 중간 상태라 되돌릴 지점이 여러 개 있어서,
`AskUserQuestion`으로 정확히 어느 버전을 말하는지 확인한 뒤(옵션 2:
"안 기울었을 때 사이즈가 정확했던 버전"), **그 상태를 손으로 다시
재구성해서 복구**했다:

- `_waterBands`: `WaterMaskRoot` 회전 피벗과 정확히 같은 점에 앵커, 자기
  pivot도 그 점 — 넉넉한 정사각형 크기(병 높이의 2.2배)로 항상 고정.
- 세그먼트: `_waterBands` 폭 전체로 가로 스트레치(`anchorMin.x=0,
  anchorMax.x=1`), 세로는 `RelayoutSegments`가 매번 `FillArea.GetWorldCorners()`로
  직접 측정해서(상수 아님) 배치.
- 즉 **세로 크기 버그는 고쳐진 채로, 가로가 병보다 넓어 보이는 버그는 아직
  남아있는 상태**다 — 이게 사용자가 "그래도 느낌은 거의 근접했다"고 평가한
  지점이었다.

"물이 기울 때 뻣뻣해 보인다"는 원 지적과 별개로, 이 세션에서 가로 폭
문제를 고치려던 두 번의 후속 시도(바운딩 박스 기준, 중심축+진짜 폭 기준)
모두 회전 기하학을 잘못 짚어 더 나쁜 결과를 냈다 — 그래서 가로 폭 수정은
지금 다시 시도하지 않고, 사용자가 확인 후 다음 방향을 정할 때까지 이
체크포인트에서 대기한다.

**다섯 번째 시도 — WaterClip(FillArea 크기의 별도 Mask), 결과 대기 중**:
사용자가 다시 요청 — 정확한 진단은 "물이 보여지는 범위 자체가
`WaterMaskRoot`(병 전체 캔버스 크기의 유리 실루엣) 크기여서 생기는 문제니,
`FillArea` 크기로 바꿔달라"는 것. 이전 네 번의 시도가 전부 "세그먼트
자신의 폭/위치 값"을 회전 기하학으로 직접 계산하려다 실패했던 것과 달리,
이번엔 세그먼트 크기 계산은 그대로 두고(`_waterBands` 폭 전체 스트레치,
바뀐 것 없음) **보여지는 범위 자체를 별도 Mask로 잘라내는** 접근이다:

- `FillArea` 밑에 `WaterClip`이라는 패널을 새로 만든다 — `FillArea`와
  정확히 같은 크기(앵커 0,0~1,1, 오프셋 0)로 스트레치하고, 불투명
  (`Color.white`)으로 채운 뒤 `Mask` 컴포넌트를 건다(`showMaskGraphic=false`
  라 화면엔 안 보이고 클리핑만 함). `FillArea` 자신의 Image는 완전 투명
  (알파 0)이라 그대로 Mask를 걸면 알파 클립 판정에 걸려 안쪽 내용이 통째로
  안 보이므로, 이렇게 불투명한 별도 패널을 하나 더 둬야 했다.
- `WaterMaskRoot`의 기존 Mask(`bottle_mask` 실루엣)는 그대로 둔다 — 두
  Mask가 중첩되면 Unity가 스텐실 깊이를 자동으로 누적해서 정상적으로 같이
  동작한다(공식 지원 기능). `WaterMaskRoot`의 Mask는 이제 실루엣 모양은
  유지하되 실제로 병 폭을 제한하는 역할은 더 좁은 `WaterClip`이 대신한다.
  일부러 회전하는 콘텐츠(붓는 병)에 Mask를 또 하나 겹치는 셈인데, 이미
  `WaterMaskRoot`의 Mask 자체가 회전하는 콘텐츠에서 문제없이 동작하고
  있었으므로(물이 대략 병 모양으로는 잘려 보이고 있었음 — 그냥 그 범위가
  너무 넓었을 뿐) "회전 콘텐츠 + Mask가 원인 불명으로 안 먹혔다"는 훨씬 전
  이력과는 다른 상황이라고 판단했다.
- `_waterBands`를 `WaterMaskRoot` 밑이 아니라 이 `WaterClip` 밑으로 옮겼다.
  `_waterBands`의 회전축 정렬(점-앵커 트릭)은 `WaterMaskRoot` 좌표계 기준
  `(0.5, VisualPivotY)` 지점을 썼었는데, 부모가 `WaterClip`(=`FillArea`와
  같은 크기지만 `Root`보다 작고 위치도 다른 서브 사각형)으로 바뀌었으니 같은
  월드 지점을 `FillArea`의 트리밍 비율(`fillNormalized`, 이미 계산해 둔 값)
  기준으로 다시 환산했다 — 안 그러면 회전축 자체가 미묘하게 어긋나 기울일 때
  위치가 밀리는, 이전에도 여러 번 겪었던 종류의 버그가 재발할 수 있었다.

이 방식은 세그먼트의 폭/위치 계산 로직(회전 기하학, 지금까지 네 번 다
틀렸던 부분)은 전혀 안 건드리고, 그 바깥에 "정확한 크기의 틀"을 하나 더
씌우는 것이라 실패 지점이 훨씬 적다는 게 설계 의도다.

**결과 — 동작 확인됨**: 사용자가 Unity에서 테스트하고 "원하는대로 됐다"고
확인했다(2026-09-10). "회전 콘텐츠 + Mask" 조합이 이 구조에서는 정상
동작한다. 가로 폭이 병 밖으로 삐져나오던 문제는 이걸로 해결됐다.

**후속 요청 — 수면 상한을 주둥이로 낮춤**: 확인 시점에 한 가지 더 —
기울였을 때 물이 병 입구(주둥이)보다 위에서 나오는 것처럼 보인다는 피드백.
원인은 `RelayoutSegments`가 세로 범위 상한(`maxY`)을 "회전한 FillArea 네
모서리 중 가장 높은 y"로 잡고 있어서였다 — 그 점은 입구 위쪽 변의 *먼*
모서리(참고 이미지의 빨간 원)라, 실제로 물이 쏟아지는 주둥이(입구 위쪽
변의 두 모서리 중 *더 낮은* 쪽, 파란 원)보다 위다. 수정: 상한을
`spoutY = Mathf.Min(tlY, trY)`(입구 두 모서리 중 낮은 쪽)로 바꿨다. 바닥
(`minY`)은 그대로 네 모서리 중 가장 낮은 점. 안 기울었을 때는 두 입구
모서리 y가 같아서 예전과 동일(회귀 없음).

**후속 요청 — 붓는 동안 각도가 고정이라 물만 쑥 내려가 부자연스러움
(2026-09-10)**: 붓기 phase 2에서 붓는 병 각도가 `PourTiltAngleDeg`(65°)로
고정인 채 물 유닛만 줄어드니, 물줄기는 주둥이에서 나오는데 병 속 물 수면은
그보다 한참 아래로 내려가는 그림이 됐다. 사용자 제안: "물이 줄어드는 만큼
병을 점점 더 기울이면 남은 물이 계속 주둥이에 붙어 보인다."

기하학적으로 맞는 직관이다 — `RelayoutSegments` 모델에서 기울어진 물 영역의
세로 높이는 `spoutY - minY ≈ 2·(병 반높이)·cosθ`라, θ가 커질수록(수평에
가까울수록) 줄어서 수면(`minY + 채움비율·(spoutY-minY)`)이 `spoutY`(주둥이)에
가까워진다. 다만 채움비율이 1(가득)이 아닌 이상 90° 전에는 수면이 주둥이에
정확히 닿진 않으므로, 이건 "완전 해결"이 아니라 "간격을 많이 줄이면서 붓는
동작 자체를 자연스럽게"다.

**구현** (`PourAnimator.PlayRoutine` 2번, `UiTheme.PourFlowEndTiltAngleDeg = 80f`):
- phase 2 동안 각도를 `Mathf.Lerp(fullAngle, pourEndAngle, p)`로 물 유닛
  변화(같은 `p`)와 같은 속도로 눕힌다.
- 각도가 바뀌면 주둥이 위치도 움직이므로, 매 프레임 `SpoutWorldPosition`을
  측정해서 `root.position += hoverSpoutTarget - measuredSpout`로 보정 —
  주둥이가 계속 도착 병 입구 바로 위에 고정돼 물줄기가 대각선으로 안 틀어진다.
  병진이동은 회전과 무관해서 이 한 스텝 보정이 근사가 아니라 정확하고, 매
  프레임 재측정이라 자기보정된다(phase 1의 `hoverRootTarget` 계산과 같은 패턴).
- phase 3(복귀)는 `pourEndAngle`·`pourEndRootPos`(2번 마지막 보정값)에서
  0/제자리로 되돌린다.
- 80°는 `atan(병높이/병폭) ≈ 74°`를 넘겨 "주둥이가 병에서 제일 낮은 점"이
  되는 구간이라 "물이 주둥이에 고인다"가 물리적으로도 말이 되지만, `2h·cosθ`가
  0으로 붕괴하는 건 90°에서만이라 세그먼트가 사라지진 않는다. 더 눕히면 병이
  쓰러져 보여서 여기서 멈춤(사용자가 값 조정 가능).

## 사운드 시스템 + 설정 창 (2026-09-10)

그동안 사운드는 붓기 효과음 슬롯(`UiSkin.PourSound`) 하나만 있고 그마저도
`PourAnimator`가 자기 `AudioSource`로 직접 재생하는 임시 구조였다. 사용자가
설정 창(참고 이미지: BGM/SFX 각각 ON·OFF 토글 + 볼륨 슬라이더 + CLOSE)을
요청하면서, 나중에 클립만 만들어 Inspector에 드래그하면 바로 붙을 수 있게
사운드 종류를 미리 나눠 두라고 했다.

**클립 슬롯 (`UiSkin`)**: `MainBgm` + SFX 5종 —
`ButtonTouchSfx`(새로고침 뺀 모든 버튼·물병 탭 공용), `RefreshSfx`(초기화
버튼 전용), `PourSound`(물 따르기), `BottleCompleteSfx`(한 색으로 병 완성),
`StageClearSfx`. 전부 비워도 그 소리만 무음이고, 나중에 넣으면 재컴파일
없이 동작(각 재생 시점에 `UiTheme.Skin`에서 새로 읽음).

**`SoundService`(신규, UI)**: 앱에 하나뿐인 `MonoBehaviour`. `GameBootstrap`이
`DontDestroyOnLoad` 루트에 붙여서 타이틀↔게임↔클리어를 오가도 BGM이 안 끊긴다.
`AudioSource` 3개 — BGM(loop), SFX(`PlayOneShot`, 겹침 허용), Pour(전용).
카메라가 없어 씬에 `AudioListener`가 없을 수 있어 없으면 자기 GO에 하나 붙인다.
`PlayPour()`는 **이전 재생을 끊고 다시 시작** — 여러 병을 동시에 옮겨도 붓기
소리가 겹쳐 뭉개지지 않고 "가장 최근 붓기" 하나만 들린다(물줄기 z-order를
"나중 것 우선"으로 두는 기존 정책과 같은 결).

**설정 저장 (`SettingsStore`, 신규, Managers)**: `HintStore`/`ProgressStore`와
같은 `PlayerPrefs` 래퍼. BGM/SFX 각각 `Enabled`(bool) + `Volume`(0~1). "끔"은
볼륨과 별개 — 끄면 볼륨 값과 무관하게 `EffectiveVolume`이 0. `SoundService.ApplySettings`가
이 값을 세 소스 `volume`에 반영(끄면 0, 재생은 계속되므로 다시 켜면 즉시 원복).

**설정 창 (`SettingsDialog`, 신규)**: `ConfirmDialog` 패턴(Canvas 직속, 딤 배경,
고정 크기 패널, 절대 좌표). 여는 쪽 `TitleScreen.RequestSettings`가 `_activeDialog`로
잡아 Escape/CLOSE로 닫는다(게임 화면엔 설정 버튼이 없으므로 타이틀에서만 진입).
`UiFactory.CreateSlider`(신규 — 스프라이트 없이 트랙/채움 단색 + 핸들만 circle.png)로
슬라이더를, 토글은 `SettingsDialog` 안에서 직접(색·글자를 눌릴 때마다 교체).
ON/OFF 토글 버튼 배경은 `UiSkin.ToggleButtonBackground`(Inspector 슬롯, 없으면
단색). 제목 폰트는 공용 `DialogTitleFontSize`(56)가 아니라 전용
`SettingsTitleFontSize`(68), 세 그룹(제목 / BGM·SFX / CLOSE) 사이 간격을 넉넉히
두려고 패널 높이를 620→720으로 키웠다. 볼륨 기본값은 100%가 아니라 50%
(`SettingsStore`의 `GetFloat` 기본 인자 0.5) — 전부 2026-09-10 사용자 확정.

**버튼 효과음 배선**: `UiFactory.CreateButton`/`CreateIconButton`에 옵셔널
`SoundService.Sfx? clickSfx = ButtonTouch`를 추가해서, 팩토리로 만든 모든
버튼이 기본적으로 터치음을 낸다. 초기화(RESET) 버튼만 호출부에서
`clickSfx: Sfx.Refresh`로 덮어쓴다. 물병 탭은 `GameView.OnBottleTapped`에서,
병 완성음은 완성 버스트와 같은 자리에서, 스테이지 클리어음은
`StageClearOverlay.Play` 시작에서 각각 명시적으로 재생한다.

  시점은 아직 안 다뤘다 — 필요해지는 시점에 `개인정보처리방침_재사용_가이드.md`를
